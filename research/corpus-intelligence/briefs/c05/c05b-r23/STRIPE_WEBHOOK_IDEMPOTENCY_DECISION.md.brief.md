# docs/ops/STRIPE_WEBHOOK_IDEMPOTENCY_DECISION.md
## What it is (1-2 sentences)
Decision record (doc-only, zero code diffs) resolving research card CARDS_LAUNCH_QA.md LQ7 (paywall audit, LOW): the Stripe webhook route has a check-then-handle-then-record window where concurrent duplicate deliveries can both execute the handler, and the record recommends Option C (documented invariant + idempotency test) for launch, Option A (insert-first status claim) post-launch.
## Key metrics/methods (formulas where given, else "not specified")
- The window (apps/web/app/api/webhooks/stripe/route.ts): (1) `db.webhookEvent.findUnique({ where: { stripeEventId: event.id } })` idempotency check; (2) if unseen, `await handleStripeEvent(event)` runs entitlement/subscription sync; (3) only after success, `db.webhookEvent.create(...)` records it. Two concurrent deliveries of the SAME event both pass step 1 before either reaches step 3 → both execute the handler. Stripe does send duplicates (at-least-once delivery, dashboard "resend", retries on slow 200).
- Option A — status-column insert-first: `create({ stripeEventId, status: PROCESSING })` first (unique constraint = the claim; concurrent create gets P2002 and skips BEFORE running handler, closing the window structurally); on success `update({ status: COMPLETED, completedAt: now() })`; on failure `update({ status: FAILED })` (or delete claim) so legitimate Stripe retries of failed deliveries aren't blocked. New enum `WebhookEventStatus { PROCESSING, COMPLETED, FAILED }`. Rejected for launch: needs Prisma migration (forbidden zone `packages/db/prisma/`; migrations are founder-applied, not run unattended).
- Option B — `pg_advisory_lock`: rejected on this stack. `DATABASE_URL` (pooled `-pooler`) vs `DIRECT_URL` (non-pooled direct) is a deliberate Neon pattern; PgBouncer transaction-mode pooling releases session-scoped locks when the transaction ends, not when the app releases, so the window reopens silently; `pg_advisory_xact_lock` would need the whole handler in one DB transaction, but handlers call external services (Stripe re-fetches, `track()` analytics) that must not sit inside an open transaction.
- Option C — accept convention, enforce it: (1) document invariant above `handleStripeEvent`'s switch: every `case` MUST re-retrieve current state (Stripe and/or DB) before writing and converge to the same end state whether run once or twice — no appends, increments, or non-idempotent side effects (e.g. one-shot notifications) without their own dedupe key; (2) structural test: for each `event.type` in the switch, call `handleStripeEvent(event)` twice against the same starting DB state and assert identical resulting DB rows (subscription tier, webhookEvent count, other tables) — compares resulting state, not call arguments.
- Cost of Option C: two concurrent deliveries still both run the handler (wasted work, one duplicate `track()` analytics call) — harmless but not prevented.
