# ops/archive/dated/ZK_PROOF_EVOLUTION_ROADMAP.md
## What it is (1-2 sentences)
Design-locked, phased roadmap (dated 2026-07-10) for evolving the pick-proof cryptographic trust layer from SHA-256 Merkle receipts (live) through Pedersen commitments (live/dark), to Halo2 recursive zero-knowledge proofs (Phase 1, 4–6 weeks engineering), and optional STARK post-quantum proofs (Phase 2, 8–12 weeks) — with Merkle remaining the root of trust at every phase and CI-enforced overclaim guardrails.
## Key metrics/methods (formulas where given, else "not specified")
- Pedersen commitments: additively homomorphic; perfectly hiding, computationally binding (~128-bit DLOG). NOT ZK in the proof-system sense; NOT post-quantum (DLOG falls to Shor). Implemented in `packages/crypto/src/pedersen-ledger.ts` using secp256k1 via @noble, constant-time.
- Halo2/IPA recursion: constant proof size ~3–5 KB; verification <60 ms on mobile; NO trusted setup in the recursive configuration. Explicit correction: Halo2/IPA recursion is discrete-log-based and is NOT post-quantum.
- STARK: hash-based (FRI), transparent, post-quantum under standard hash assumptions; larger proofs (tens of KB), slower provers.
- Phase 1 Halo2 circuit uses fixed-point arithmetic (scale 1e6) for the 52.4% boundary; pushes excluded exactly as `settlement.ts` grades them.
- `CommitmentEnvelope` interface: `merkleProof: MerkleProof` (live, never removed), optional `pedersenAggregate?: Commitment`, optional `zkProof?: { type: "halo2" | "stark"; data: Uint8Array }` (null until live+audited), `publicInputs: { aggregateClv: number; N: number; merkleRoot: string }`. Verifier order: Merkle → Pedersen → zkProof.
- Overclaim fence: `scripts/guardrails/no-zk-overclaim.mjs` (CI-blocking) blocks any public "zero-knowledge"/"post-quantum" language until the corresponding system is live AND externally audited; Pedersen opener boundary fenced in CI by `scripts/guardrails/pedersen-opener-boundary.mjs` (+ fixtures).
- Phase 0.5 opener: `planSlateOpening` (@sports/crypto) — pure, DB-free, REFUSE by default; opener reads exactly one module (`packages/ingestion-pipeline/src/slate-opening-reader.ts`); opens only when (1) slate fully settled, (2) opener exists, (3) opener verifiably reproduces published hex. Gate env: `SLATE_OPENING_REVEAL_ENABLED`, unset in git.
- Phase ordering gate: each phase gated on previous being "boringly stable"; every phase ships with failing-then-passing tests and explicit rollback (drop the optional envelope field).

## Findings (numbers and facts, not vibes)
- Status at doc date (2026-07-10): Merkle receipts LIVE (minted per pick pre-kickoff via `process-sport.ts`, publicly verifiable at `/verify`); Pedersen LIVE but SEALED-SIDE ONLY (minted per frozen slate by `freeze-slate-commitments.ts`; only public hex served via `/api/verify/slate`; openers `pedersenAggregateValue`, `pedersenBlindingSum` stay server-side).
- Phase 0.5 aggregate minted inside the SAME atomic transaction as the Merkle root (write-once, never backfilled onto a frozen slate); fails open — unencodable slate mints nothing rather than blocking the Merkle path.
- Phase 0.5b (`SLATE_OPENING_REVEAL_ENABLED` gate): planner refuses unless all three conditions hold; settlement checked BEFORE opener parsed so no code path touches the secret while slate is live; "a mostly-settled slate is not partly openable — the aggregate is one number over the whole population."
- Third refusal rationale: stored opener must reproduce stored hex, otherwise opening is WITHHELD because "publishing an opener that fails in the customer's hands would read exactly like a forged commitment."
- Public language rule: "commitment" only — never "ZK", never "post-quantum" (until audit unlocks); only then may "zero-knowledge" enter ALLOWED_PHRASES in the guardrail, citing the audit.
- Anti-cherry-picking story: Merkle + Pedersen aggregate of "published edge scores" over a frozen slate.
- Phase 1 E2E test shape: freeze synthetic slate → prove → verify → aggregate matches without opening picks.
- Phase 2 is optionality, not replacement — run beside Halo2 if/when quantum timelines demand it; "priced accordingly."
- 52.4% boundary: the break-even win-rate boundary for -110 bets used in the fixed-point circuit arithmetic (scale 1e6); CLV milestones also measured against ≥52.4% (corroborates the CLV/pricing-ladder docs elsewhere in corpus).
