# ops/edge/2026-08-19-odds-widget-integration-design.md

## What it is (1-2 sentences)
A design-only document (no app code changed, read-only pass as of 2026-08-19) for integrating The Odds API's vendor-hosted affiliate widget into the Galaxy Sports Edge web app: a `<script>`-tag embed carrying a bookmaker's odds plus an affiliate click-through link, modeled through the existing `apps/web/lib/revenue/` partner/offer system as a **revenue placement, not a data source**, strictly structurally separated from the prediction engine and pick UI.

## Findings (numbers and facts, not vibes)
- `THE_ODDS_WIDGET_KEY` is a second, distinct secret from `THE_ODDS_API_KEY`; the widget is a vendor-hosted, vendor-branded embed (script tag + config div/data-attributes) rendering one bookmaker's odds with an affiliate click-through.
- Placement recommendation: picks-page footer (`apps/web/app/picks/page.tsx`, below pick grid, above `<Footer />`) first; dedicated `/odds` page as v1.1 follow-up; dashboard sidebar explicitly not recommended for v1 (confidence-dense authenticated surface, highest conflation risk).
- The widget must be classified `category: "sportsbook"`, NOT `"sports_data"`, because it terminates in a bookmaker click-through with money downstream; `sports_data` classification would bypass the entire high-risk compliance bundle (terms URL, responsible-gaming text, 21+ policy, state lists).
- Adding the widget requires the new `"odds_widget"` surface in **three** places: `partner-types.ts` (not sealed), `scripts/guardrails/partner-offer-compliance-scan.mjs:17-27` `VALID_SURFACES` (**sealed, owner-delegated — the one hard dependency blocking end-to-end shipping**), and the second copy of the union in `apps/web/lib/fences/affiliate-disclosure-fence.ts:41-55` (not sealed).
- Structural separation rule: widget DOM must never be inside or adjacent-without-separation to a `PickCard` (`apps/web/components/picks/pick-card.tsx:87-118+`), never inside the picks grid (`page.tsx:525-535`), in its own bordered `<section>` card with its own heading and adjacent disclosure, using visually distinct treatment from the pick-grade palette (`PICK_GRADE_STYLES`, `pick-card.tsx:25-30` — plasma/verify/ion-blue) plus explicit "not a Galaxy Sports Edge pick" labeling.
- The existing `affiliate-structural-separation.mjs` guard (header lines 1-36, target lists 51-93, `SPECIFIER_RE` line 49) checks **import-graph** separation only, not rendered UI — passing it is necessary but not sufficient for the UI conflation requirement; any widget-key resolver must live under `apps/web/lib/` (never `packages/data-ingestion/` or `packages/prediction-engine/`).
- **Gap surfaced**: `evaluateOfferEligibility` takes `userState` as input (`offer-eligibility.ts:29`) but the repo has no geolocation/account-state signal feeding it; under the platform's own fail-closed rule, the widget **cannot legally render for anonymous traffic at all** without one — a founder scope decision, flagged explicitly.
- **Adjacent gap (not this feature)**: nothing in `apps/web/lib/revenue/` records whether a click-through actually converted; S2S postback tracking (webhook + HMAC/shared-secret verification + idempotency) is a separate design pass owed for all affiliate partners.
- Eight founder/owner review items listed (§5): which bookmaker(s) the key activates, real state licensing lists, user-state signal source, partner/offer approval flip, live vendor script-host/mechanism check, sealed-guard `VALID_SURFACES` addition, legal copy review, placement confirmation.
- Safe-to-build-in-a-PR list (6 items, no compliance risk): enum edits, server-only env resolver (wired to return `""`/absent until confirmed — a safe no-op), inert partner/offer records with `"unreviewed"`, a placeholder-labeled scaffold component gated behind `evaluateOfferEligibility`, and mirroring tests (`apps/web/__tests__/affiliate-compliance.test.ts`, `apps/web/lib/revenue/offer-eligibility.test.ts`). Explicitly forbidden in that PR: the CSP origin addition and any real vendor script/bookmaker terms/state data.
