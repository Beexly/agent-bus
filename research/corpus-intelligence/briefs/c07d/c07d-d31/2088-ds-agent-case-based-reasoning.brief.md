# arxiv-program/research/2026-09-21/arxiv-deep/2088-ds-agent-case-based-reasoning.md
## What it is (1-2 sentences)
A full-paper read (ar5iv HTML, Abstract + Sections 1–4) of DS-Agent (arXiv:2402.17453, Guo, Deng, Wen et al., 2024; v5 verified via export API): an LLM data-science agent that replaces ungrounded experiment planning with classical case-based reasoning (retrieve → reuse → revise → retain) over a bank of expert Kaggle solution reports, in a two-stage design — iterative development stage plus cheap single-pass deployment stage. The file's verdict is ADAPT: the CBR cycle is the memory discipline for the MOVE-37 execution lab, and the two-stage split maps to nightly discovery vs. cheap weekly production re-runs.

## Key metrics/methods (formulas where given, else "not specified")
- Formalization (Section 2): retriever p_R (distribution over the case bank given task τ and feedback l), LLM p_LLM (generates solution y given τ, l, retrieved case c), evaluator p_E (produces feedback l from y).
- Iteration-t solution distribution: p_CBR(y^t|τ) marginalizes over retrieved-and-revised cases; differs from RAG by the revise + retain steps (RAG only retrieves/reuses once).
- Feedback distribution: p_E(l^t|τ) = Σ_{y^t} p_CBR(y^t|τ) p_E(l^t|y^t,τ).
- ReviseRank utility: p_RR(c|τ,l^{t−1}) = p_LLM(c|c_1,...,c_k,τ,l^{t−1}) — LLM re-ranks cases as "[2]>[1]>[3]..." conditioned on last iteration's execution feedback; dynamic case adjustment WITHOUT retriever fine-tuning.
- Development stage: (1) retrieve top-k by embedding similarity; (2) ReviseRank; (3) planner reuses top case to write experiment plan; (4) execute, get feedback l^t; (5) loop; (6) Retain — best solution added to the case bank (flexible learning without backprop).
- Deployment stage: simplified CBR — retrieve past successful development solutions, reuse with minor adaptation, single pass, no iteration; designed for weak LLMs (knowledge transfer via a similar case in context).
- Case bank: technical reports of winning teams + top-ranked public-leaderboard code from several recently completed Kaggle competitions (text, time-series, tabular); reports cleaned to core insights; code summarized to textual insights via GPT-3.5.
- Evaluation: 30 data-science tasks — 12 development (iterative) + 18 deployment (single-shot). Each task = (description τ, D_train, D_valid, D_test, metric M). Baselines: ResearchAgent and others with GPT-3.5/GPT-4/Mixtral-8x7b. Metrics: task success rate, one-pass rate, mean/best rank vs baselines (5 repetitive trials).
- Assumptions: Kaggle expert insights transfer to new tasks; LLM-estimated case utility correlates with true utility; retaining best solutions monotonically improves the bank; deployment tasks share the development distribution.
- GSE implementation spec: case schema in SQLite — (case_id, hypothesis_text, feature_code, backtest_spec, feedback_log (the 2084 reflections), dev_score (2025-holdout ΔBrier), stage3_score (locked-season), retained_flag, embedding); seed with the 5 hand-verified baseline signals + every future discovery-loop attempt INCLUDING failures (cf. DGM stepping stones, 2086). Development stage (nightly): generator retrieves top-k by embedding similarity; ReviseRank LLM re-ranks conditioned on last night's feedback; planner writes plan reusing top case; executor runs; retain if it passes the Stage-2 gate. Deployment stage (weekly, cheap): retrieve current best production-pipeline case, regenerate weekly model-fit code with minor adaptation — runnable on a small/cheap model. Effort: 2 days (schema + retriever + ReviseRank prompt + retain logic) on top of the 2082 harness.
- Reproducible test: nflverse 2015–2024 + 2025 holdout. (a) Build case bank from 20 hand-logged past GSE-style experiments (10 successes, 10 failures with feedback notes); (b) discovery loop on 10 new signal hypotheses with CBR retrieval vs without (cold start). Metrics: gate-pass rate within a 5-iteration budget; mean iterations-to-pass; deployment test — regenerate the production spread-model fit script from the best case using a small model, measuring one-pass success (code runs, reproduces baseline Brier within 1e-4).
- Acceptance gate: ADOPT if CBR arm passes ≥6/10 hypotheses within budget vs ≤3/10 cold-start; ReviseRank demonstrably demotes at least one misleading case per night on average; deployment-stage regeneration succeeds one-pass ≥80% of weeks over 8 weeks with the small model. REJECT if cold-start matches within 1 hypothesis (retrieval adds nothing — bank too small or embeddings uninformative), or retained cases show score decay on re-run (bank poisoning — retain criterion too lax), or ReviseRank rankings are uncorrelated with next-iteration outcomes (LLM can't estimate case utility → drop ReviseRank, keep static retrieval).
- Improvement experiment (beyond the paper): COUNTER-CASE retrieval — for each retrieved success case, also retrieve the most similar FAILED case and inject its feedback ("this similar idea failed because of X") into the planner prompt. Hypothesis: negative cases prevent repeating known failure modes faster than positive cases guide success. Test: 10 hypotheses, planner with success-only vs success+counter cases, measuring wasted iterations on already-known failure modes.

## Data sources named
- Kaggle competitions: technical reports of winning teams + top-ranked public-leaderboard code (text, time-series, tabular modalities). Summarized via GPT-3.5.
- Baselines: ResearchAgent (GPT-3.5/GPT-4), Mixtral-8x7b.
- Code: open-sourced at https://github.com/guosyjlu/DS-Agent.
- GSE-internal: nflverse 2015–2024 + 2025 holdout for the reproducible test; 2084 reflections as the feedback log; 2086 (DGM stepping stones) for failure retention; 2082 harness as the build base.

## Findings (numbers and facts, not vibes)
- Development: DS-Agent + GPT-4: **100% success rate** over all 12 tasks; best performance in 9/12 tasks. DS-Agent + GPT-3.5 second-best overall, "consistently surpasses ResearchAgent with GPT-4 in all tasks". ResearchAgent + GPT-3.5 "almost fails in every type of task".
- Deployment: one-pass rate **85% (GPT-3.5) / 99% (GPT-4)** over 18 tasks vs best baseline 56% / 60%. Mixtral-8x7b-Instruct lifted from **6% → 31%** by the simplified CBR (36% average one-pass-rate improvement across alternative LLMs, per the abstract).
- Iteration scaling: average best mean rank improves monotonically with iteration steps (Figure 1b).
- Cost: $1.60/run (GPT-4) / $0.06 (GPT-3.5) development; $0.135 / $0.0045 in low-resource deployment.
- Tabular tasks easiest (mostly sklearn calls); time-series/text harder.
- Leakage/limitations in file: Kaggle case bank may overlap pretraining data (memorization vs reasoning unmeasured); deployment-stage transfer assumes same task distribution (untested on distribution shift); the ReviseRank LLM re-ranker is itself uncalibrated (no reported ranking accuracy); mean-rank metrics hide per-task variance; tabular-task ease inflates headline numbers.
- GSE-critical caveats in file: the case bank must be GSE's own verified experiments (not Kaggle), or the agent retrieves patterns that don't transfer to sports betting; the retain step needs the deterministic gate — retaining a lucky backtest poisons the bank (the paper retains by validation metric; in betting this must be the holdout gate, not in-sample fit).

## Intelligence connections (tag each: QB-BEHAVIOR, COACHING, OL, TRUST-SIGNAL, SCHEME, OTHER)
- OTHER (MOVE-37 execution lab / continuous-learning engine): the CBR cycle (retrieve→reuse→revise→retain) is explicitly the memory discipline for the MOVE-37 lab in the file's GSE-overlap section — every backtest the lab runs becomes a retained case (hypothesis + code + feedback + outcome), and future discovery retrieves and revises those cases instead of starting cold. Mechanism: ReviseRank re-ranks cases conditioned on last night's execution feedback WITHOUT retriever fine-tuning, so the lab learns from failures overnight while the embedding index stays static. The file's retention schema (case_id, hypothesis_text, feature_code, backtest_spec, feedback_log, dev_score, stage3_score, retained_flag, embedding) is directly the discovery-loop ledger. Relevant program: MOVE-37 discovery + continuous-learning engine.
- OTHER (engine cost architecture): the development/deployment two-stage split is the cost mechanism for the engine — nightly iterative discovery on the strong model vs. weekly cheap single-pass regeneration of the current best production pipeline on a weak model. The Mixtral 6%→31% result is the file's precedent that weak models + good retrieved cases are viable for the deployment stage. Relevant program: calibration/sizing (operational cost of the weekly model-fit cycle).
- OTHER (calibration/sizing, negative-evidence discipline): the counter-case improvement experiment (retrieve the most similar FAILED case alongside each success case and inject its failure feedback into the planner prompt) is a mechanism against the known pathology of retesting dead hypotheses — failures with feedback notes are first-class citizens of the bank, seeding from 10 successes + 10 failures with feedback notes. Relevant program: trust-target intake (pruning known-dead signal families before spending budget).
- UNCERTAIN: whether ReviseRank rankings correlate with next-iteration outcomes when the LLM is weak — the paper never reports ReviseRank ranking accuracy, and the acceptance gate pre-registers dropping ReviseRank (keeping static retrieval) if rankings are uncorrelated with outcomes. Mechanism risk: an uncalibrated LLM re-ranker could demote the right cases.

## Engine-actionable? (yes/no + one-line what)
Yes — build the GSE case bank in SQLite with the full feedback/outcome schema (including failures), implement retrieve→ReviseRank→plan→execute→retain on the 2082 harness (~2 days), and add counter-case retrieval so every planner prompt sees the most similar known failure alongside each success; the retain step gates on the holdout (not in-sample) score to prevent bank poisoning.
