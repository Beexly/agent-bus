# ai/jarvis/JARVIS_MEMORY_BUILD_SPEC_2026-06-12.md
## What it is (1-2 sentences)
The owner's verbatim build spec (2026-06-12, QUEUED — not yet built) for wiring Jarvis persistent memory: an evidence-based, typed, timestamped, source-linked, reviewable, reversible Postgres episodic store plus an optional mem0/vector recall layer, so the system remembers decisions, doctrine, failures, and preferences across sessions without inventing facts.
## Key metrics/methods (formulas where given, else "not specified")
- Canonical memory hierarchy: (1) version-controlled markdown (architecture/doctrine source of truth); (2) Postgres episodic memory store (decisions/events/lessons/failures/approvals); (3) vector / mem0 retrieval layer — optional recall/index only, never canonical; (4) runtime context (current session only). No numeric formulas.
- Memory categories: Episodic (what happened) · Semantic (what is true) · Procedural (how Jarvis does things) · Preference (how Garrett prefers decisions/outputs/escalation) · Decision (what was decided, why, by whom, when) · Failure (what went wrong, what changed, recurrence prevention).
- Memory states: candidate · confirmed · repeated_pattern · conflicted · stale · superseded · rejected · expired. Memory must not become permanent because a model inferred it — candidates require confirmation, repeated evidence, or explicit owner approval.
- Memory types for the table: episodic, semantic, procedural, preference, decision, failure, source, agent_performance, escalation_rule, public_claim_rule.
- Retention per memory: no expiration · 30-day · 90-day · project-based · superseded. Don't keep temporary operational detail forever unless it materially improves future decisions.
- Acceptance criteria (12): (1) Jarvis can write a memory candidate from an owner decision; (2) confirm / reject / edit / expire / supersede all work; (3) confirmed memory persists across reloads and sessions; (4) relevant confirmed memories recalled before answering; (5) candidate memory never treated as confirmed fact; (6) conflicts surfaced, never overwritten; (7) every memory has type, state, timestamp, source, confidence; (8) major decisions create decision-ledger entries; (9) panel clearly shows Wired / Not Wired / Partial / Simulated; (10) mock memory data clearly labeled simulated; (11) linked to Forecast Center, Owner Brief, Model Council, Learning Loop, Failure Autopsy; (12) Jarvis can answer: "What did we decide, when, why, on what evidence, and did it work?"

## Findings (numbers and facts, not vibes)
- Current state: memory is NOT wired. Jarvis has no persistent memory; operational truth is rebuilt from the database on every load; architectural truth lives in version-controlled markdown; nothing is reliably recalled across sessions.
- Core principle: Jarvis memory must be evidence-based, typed, timestamped, source-linked, reviewable, and reversible. Do not treat memory as vague chat history; do not let self-learning become self-corruption; do not let vector memory become the source of truth.
- AI Ops panel — "Jarvis Memory Protocol" — shows: memory status (Wired / Not Wired / Partial / Simulated) · persistent store (Postgres / mem0 / Not Connected) · last memory written · last memory recalled · candidates awaiting approval · conflicted · stale · expired · memory health score · next action. When not wired: "Jarvis has no persistent memory. Operational truth is rebuilt from the database on every load; architectural truth lives in version-controlled markdown. Nothing is recalled across sessions." Next action: "Wire an episodic memory store that captures owner decisions with timestamps, source references, review state, and recall metadata per JARVIS_MEMORY_PROTOCOL.md."
- Memory-worthy events (examples): owner approved a public-claims rule; owner rejected a design direction; owner changed model routing; Jarvis escalated for legal/compliance risk; a prompt repeatedly failed and was demoted; a No-Bet pattern proved valuable; a source became unreliable; a launch blocker was identified; an architectural rule was added to markdown doctrine.
- Recall behavior: before answering a meaningful owner / architecture / product / legal-sensitive / public-claims / GSE-strategy question, retrieve relevant memory — confirmed memories, relevant decisions, procedural rules, failure memories, unresolved conflicts, stale warnings. Surface transparently: "Using confirmed memory from [date]: Garrett decided X because Y." Uncertain: "I found a related memory candidate, but it has not been confirmed." Conflicting: "There are conflicting memories. Owner review is required."
- Memory hygiene flags: candidates awaiting approval · unused in 90 days · contradicted by newer decisions · low confidence · missing source references · tied to deprecated docs · should expire · need owner confirmation.
- Memory review queue: each candidate card shows proposed memory, why it matters, source, confidence, sensitivity, suggested category, and confirm/reject/edit/expire actions.
- Conflict detection: a new memory contradicting a confirmed one must NOT overwrite silently — create conflicted state; show both memories, source for each, recommended resolution; owner approval required.
- Privacy & safety: no sensitive, legal, HR, personal, or public-claim-impacting memory without clear source and review state. Public-facing claims, legal interpretations, HR-sensitive conclusions, gambling-related claims, privacy decisions, and spending authority require explicit owner confirmation before confirmation.
- Model Council integration: track over time — agents with accepted vs rejected outputs; model failures by task type; escalations; prompts promoted/demoted; failures that created procedural memory. Agent memory: trust score by task type, failure history, escalation history, last useful output, common weaknesses, approved use cases, blocked use cases.
- Owner Brief integration: daily brief includes new confirmed memories, pending candidates, conflicts needing review, decisions awaiting outcome review, failure lessons from recent runs, stale doctrine warnings.
- Non-negotiables: do not fabricate memory; do not silently promote candidates; do not overwrite confirmed memory without a supersession trail; do not let mem0/vector become the source of truth; do not bury conflicts; do not store sensitive decisions without review state; do not treat chat history as reliable operating truth; do not make memory feel magical — make it auditable.
- Final goal: Jarvis should remember consequences, not just conversations.
