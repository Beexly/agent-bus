# adr/002-jarvis-synthesizer.md
## What it is (1-2 sentences)
ADR 002 (2026-05-18, Accepted): Jarvis as a deterministic synthesizer — a pure, deterministic function answering "is the platform launch-ready?" at a glance, with no LLM call and no wall-clock-dependent inputs, so the same inputs always produce the same auditable output.
## Key metrics/methods (formulas where given, else "not specified")
- `synthesizeJarvis(input)` is a pure function over a typed `JarvisInput` returning a `JarvisAssessment` carrying: `launchStatus` (6-valued enum); `confidenceLevel` (LOW / MEDIUM / HIGH); **11** sectional health readouts (GREEN / AMBER / RED / UNKNOWN); `readinessGateSummary`; **4** warning lists (safety, missing-phase, external-config, recommended actions); `phaseMatrix` covering phases 1–9; `assessedAt`; `version`.
- Status ordering rules: LAUNCH_READY requires **zero** safety warnings; HIGH confidence requires LAUNCH_READY. No numeric formulas given.
- Purity enforcement (tested by `jarvis-purity.test.ts`): no I/O, no fs, no fetch, no `Date.now()`, no `Math.random()`, no top-level await.
- `jarvis.test.ts` asserts no `recommendedNextActions` entry contains `auto-bet` / `auto-publish`.
- `JARVIS_VERSION` is bumped on every rule change; history ring buffer via `sharedJarvisHistory()`, process-local and capacity-bound.
## Data sources named
- Inputs to the synthesizer: the readiness-gates struct; `PublicPerformancePolicy` (from ADR 001); ingestion summary (last attempt, last success, recent failures); settlement summary (last settledAt, settled-in-24h, pending count); historical pick counts by category (canonical / bootstrap / W / L / P / V / published / featured); signal coverage percentages; a hand-maintained phase-layer manifest (`const LAYERS` in `jarvis-data.ts`); list of missing external-config env vars.
- Surfaces: `/admin/dashboard` (raw operational counts), the cockpit, the JSON API, the audit log (`serializeJarvisAudit` + log file).
## Findings (numbers and facts, not vibes)
- Date: 2026-05-18. Status: Accepted.
- Motivation: existing dashboards showed raw operational counts but did not answer the readiness *question*; ad-hoc operator interpretation was inconsistent and slow. Deterministic and auditable was required: same inputs → same output every time — ruling out LLM calls and anything drifting with wall-clock time (random sampling, `Math.random()` thresholds).
- Three options were considered for how the synthesizer knows which phases are implemented: (1) runtime `fs.existsSync` of representative paths — REJECTED (fragile across deploy environments, breaks in serverless, ties synthesizer to a build layout); (2) a `package.json` manifest — REJECTED (nothing forces a contributor to update it when a phase ships); (3) a `const LAYERS` in `jarvis-data.ts` — ACCEPTED (single place, reviewed in the PR that ships the phase; reviewers see the manifest change next to the phase change).
- `PERFORMANCE_STATS_ENABLED=true` is the only operator action that changes customer-visible behavior; the synthesizer never tells the operator to "flip the gate now" — it states which conditions still block the flip; the decision stays with the human. Same for auto-publishing: never recommends "publish this draft" or "promote this pick" — both are explicit operator actions reviewed via the cockpit.
- Version stamp rationale: auditing assessments after the fact; if synthesizer rules change meaningfully (e.g. tightening the ingestion-RED threshold), the stamp lets a saved assessment be interpreted against the version that produced it.
- Jarvis-history ring buffer: supports trend display ("ingestion was AMBER 1h ago, GREEN now") and quick rollback diagnostics; process-local, capacity-bound, consumed via `sharedJarvisHistory()`; persistence beyond a single process is out of scope (pair with `serializeJarvisAudit` + a log file).
- Consequences — positive: one synthesizer, one truth; tests cover every rule; consistent picture across cockpit, JSON API, audit log; determinism + purity → reliable in CI and stub mode; composable (audit serializer, history buffer, JSON endpoint, trend component all consume the same shape).
- Consequences — negative: each rule change requires bumping `JARVIS_VERSION` and updating tests + changelog (by design — "Jarvis is the canary, and we don't want silent rule drift"); the phase-layer manifest is a maintenance burden when phases change (mitigated by single location + obvious test failure when a phase appears in the matrix as `unknown`).
## Intelligence connections (tag each: QB-BEHAVIOR, COACHING, OL, TRUST-SIGNAL, SCHEME, OTHER)
- [TRUST-SIGNAL] The deterministic-gate pattern is the model for the **calibration/sizing program's** publish gates: rules like "LAUNCH_READY requires zero safety warnings" and "HIGH confidence requires LAUNCH_READY" map directly onto "publish requires settled-evidence thresholds met" — e.g. HIGH calibration confidence only when the settled sample clears the proof bar. No LLM, no wall-clock drift, version-stamped rule changes.
- [TRUST-SIGNAL] The JARVIS_VERSION discipline (bump + tests + changelog on every rule change, no silent drift) mirrors the honest calibration-state labeling doctrine the engine already follows — a calibration rule change must leave an audit trail naming the version that produced each assessment.
- [OTHER] The canonical pick-count taxonomy — canonical / bootstrap / W / L / P / V / published / featured — is the exact bucket schema the engine should use for settled-track-record accounting behind the "≥100 settled + published calibration" proof gate.
- [OTHER] The ingestion/settlement summary fields (last attempt, last success, recent failures, last settledAt, settled-in-24h, pending count) define the ops-health signals for the **tracking lane's** settlement-monitoring dashboards; the 11-section GREEN/AMBER/RED/UNKNOWN readout is a template for engine subsystem health displays.
## Engine-actionable? (yes/no + one-line what)
Yes — adopt the deterministic, purity-tested, version-stamped gate pattern (and the canonical W/L/P/V pick-bucket taxonomy) for the engine's own publish/settlement readiness gates.
