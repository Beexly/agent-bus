# arxiv-program/research/2026-09-21/arxiv-deep/2022-managed-geo-distributed-feature-store.md
## What it is (1-2 sentences)
Deep read of the Microsoft AzureML Feature Store architecture paper (arXiv:2305.20077v1): a systems-design paper (no experiments, no numbers) distilling production learnings on offline/online stores, point-in-time joins, leakage prevention, and merge semantics. Verdict in file: ADAPT — the reference architecture for GSE's NFL feature store; Azure-specific services must be adapted (Feast + Delta Lake, not AzureML).
## Key metrics/methods (formulas where given, else "not specified")
Architecture methods: feature sets (source + transformation UDF + materialization policy) and entities (shared index/key columns); UDF signature udf(source_df, context) -> feature_df with output schema (index, timestamp, features); feature window logic: source_window_start_ts = feature_window_start_ts − source_lookback, compute on source window then filter to feature window; materialization = one-time backfill + scheduled incremental (scheduler tracks data state and job state per window; concurrent overlapping-window jobs forbidden); storage = Redis online (low-latency), ADLS Gen2/Delta offline (high-throughput); hub-and-spoke cross-region sharing; DSL query optimization; context-aware scheduling; feature-model lineage. Storage-consistency semantics (paper's eq. 1–2): offline keeps every record keyed (event_timestamp + creation_timestamp) per ID; online keeps latest record per ID assuming TTL satisfies max(tuple(event_timestamp, creation_timestamp)); merge: offline insert iff (IDs + event_ts + creation_ts) key absent else no-op; online override iff new event_ts > existing, or equal event_ts with new creation_ts > existing, else no-op. Leakage-prevention rule: for observation event at ts₀, retrieval uses only past-of-ts₀ feature values (nearest past value, accounting for expected source/feature data delay).

## Findings (numbers and facts, not vibes)
- Paper reports zero numbers — no latency, throughput, consistency-lag, or cost figures; all claims are design assertions from a production system.
- Several components (§3) are explicitly marked "aspirational... not formally implemented in the AzureML Feature Store at the time this paper is published" — the whole design must be read as part-built.
- Merge-semantics caveat (§4.5.2): "assuming that there is no failure of dumping the calculated Feature Set records" — eventual consistency under failure relies entirely on retries with no staleness bound given.
- GSE overlap: no duplication — the corpus has no feature-store/MLOps entries; GSE's current pipeline (Neon Postgres predictions DB; nflverse/FTN ingestion scripts) computes training and live-prediction features via separate code paths, exactly the train/serve-skew failure mode this paper kills.
