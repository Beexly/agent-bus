                                                                                        Abstract
                                                  Static benchmarks for computer-use agents fix a task set at release and score every system
                                              against it once. That makes them reproducible, and it lets them drift from what they should
                                              measure: a fixed task set ages, leaks into training corpora, and cannot follow how people
                                              actually use agents from week to week. CoArena measures use directly. Real users submit
                                              tasks; two systems, each a single model or a multi-agent pipeline behind the same tool
                                              interface, execute the same task concurrently in identical sandboxed desktops; users judge
                                              the two outcomes without knowing which system produced them; and a public leaderboard
                                              is refit from those judgments. The central contribution is a formal account of what makes
                                              such an evaluation real-time. We define real-time as five measurable properties, each with an
                                              equation and a worked example: continuous task arrival, live concurrent execution, online
                                              rating updates, freshness with contamination resistance, and bounded feedback latency from
                                              a failed run to a reusable training environment. The rating methodology follows in full:
                                              the Bradley-Terry pairwise model, its likelihood with weighted observations and ties, the
                                              penalized maximum-likelihood estimator, and the streaming update applied when a single
                                              vote arrives (a stochastic-gradient step on the same likelihood, recovering Elo). It gives
                                              confidence intervals from the observed information and a cluster-robust sandwich, rank bands
                                              from a parametric bootstrap, the rule by which a new system enters the board, and the
                                              convergence rate of the estimate. Vote quality is treated with inter-judge agreement statistics,
                                              redundant judging, and explicit handling of ties and abstentions. A five-system example
                                              with 211 votes is carried from the vote matrix to ratings, intervals, and rank bands. Every
                                              number is derived from stated inputs or labeled illustrative; none is a measurement of a
                                              deployed system.


                                         1    Introduction
                                         A computer-use agent receives an instruction in natural language and operates a desktop or a
                                         browser on a person’s behalf: it reads the screen, moves a pointer, types, and delivers a result.
                                         The agent may be a single model behind a fixed scaffold, or a multi-agent system that plans,
                                         delegates and verifies internally before it acts. From the outside the two look the same, an
                                         instruction goes in and actions on a screen come out, and they can be evaluated the same way.
                                         So far that evaluation has followed the pattern set for language models: a benchmark author
                                         writes a fixed set of tasks, each with a programmatic or rubric-based checker, and every system
                                         is scored against that set [6, 18, 30, 33]. The pattern has one clear virtue, reproducibility, and
                                         three structural weaknesses when the object of study is a system people actually use.



                                                                                             1
     First, a fixed task set does not track use. The distribution of tasks people ask agents to do
shifts with the software they use, the sites they visit, and the agents’ own growing capabilities.
A benchmark frozen in one year measures the workload of that year.
     Second, a fixed task set ages into the training data of the models it is meant to measure.
The concern is documented for language benchmarks [14, 27] and has motivated benchmarks
that refresh their questions on a schedule [15, 29]. A scheduled refresh reduces the problem; it
does not remove the interval during which a released task set is both public and in use.
     Third, a fixed task set is scored by a checker written in advance, and the checker encodes the
author’s notion of success. For open-ended computer work, whether an outcome is acceptable
often depends on the person who asked. Human preference between two attempts at the same
task is a different measurement, one that pairwise arenas for chatbots have collected at scale
[3, 32].
     This paper describes an arena for computer-use agents built around those three observations,
and it makes one claim precise: that the arena is a real-time evaluation. The word is used loosely
across evaluation platforms. We define it as a set of five measurable properties (Section 4),
each with notation, an equation where one applies, and a worked example. The properties
are continuous task arrival, live concurrent execution, online rating updates, freshness with
contamination resistance, and bounded feedback latency from a failed run to a reusable training
environment. Continuous arrival means the evaluation has no release epochs. Live concurrent
execution means that both agents run the same task at the same time in identical environments,
and that execution is contemporaneous with submission. Online rating updates means that the
published rating is a bounded-latency function of every admissible judgment. Freshness means
that a task is executed within minutes of being written, before any training pipeline can have
observed it. Bounded feedback latency means that a failure becomes something a developer can
train against within a stated horizon.
     The rest of the paper supplies the machinery those properties rest on. Section 3 describes the
arena concretely. Section 5 presents the rating methodology: the pairwise model, its likelihood,
the batch and streaming estimators, intervals, rank bands, entry of new agents, and convergence.
Section 6 carries a small example through the whole pipeline and treats vote quality. Sections 7
and 8 discuss limitations and conclude. Appendix A collects the notation (Table 3), Appendix B
lists the algorithms (Algorithms 1 to 4), and Appendix C walks one battle through the interfaces.
     A note on numbers. Every number in this paper is either derived from stated inputs in
the text, produced by a simulation whose generative model and seed are stated, or labeled as
illustrative. None is a measurement of a deployed system, and the reader should not interpret
any figure here as an empirical result about a particular product.


2    Related Work
Paired-comparison models. The model we use for ratings originates with Zermelo’s treat-
ment of chess tournament results [31] and was developed independently by Bradley and Terry [2].
Ford gave the condition under which the maximum-likelihood estimate exists: the comparison
graph must be strongly connected in the sense that every agent has both a win and a loss path
to every other [10]. Hunter analyzed minorization-maximization algorithms for the model and
its generalizations [13]; Newman gave an accelerated iteration [24]. Ties were incorporated by
Rao and Kupper through a threshold parameter [25] and by Davidson through a separate tie
propensity [5]. The Elo rating system [8] is the sequential update familiar from chess rating;
Glickman’s Glicko [11] and the TrueSkill system [12] add a per-player uncertainty that widens
with inactivity.

Arenas for language models. Chatbot Arena collected human pairwise preferences between
anonymized chatbots and fit a Bradley-Terry model to them, with bootstrap confidence intervals


                                                2
[3, 32]. Its authors and others have examined the robustness of Elo-style ratings to vote order
and sample size [1] and the influence of response style on human preference [20]. Our setting
differs in what is compared (a trajectory of screen actions ending in a delivered result, rather
than a text response) and in the cost of a comparison (minutes of sandboxed execution rather
than a single generation), which shapes the concurrency and queueing analysis of Section 4.

Benchmarks for computer-use agents. OSWorld [30], WebArena [33], VisualWebArena
[18], Mind2Web [6], and Android in the Wild [26] established executable environments with
fixed task sets and programmatic checkers. They remain the appropriate instrument when
reproducibility of a specific task is the goal. Our arena is complementary: its tasks are whatever
users submit, its judgments are human, and its purpose is to track use rather than to fix a target.

Contamination and refreshed benchmarks. The leakage of evaluation data into training
corpora has been measured for language benchmarks [27], and mitigations range from withholding
test data from plain-text distribution [14] to periodic refresh [15, 29] to adversarial, human-in-
the-loop data collection [16]. We treat contamination resistance as a consequence of the arrival
process: a task that is written and executed within minutes cannot have been in any training
set that closed before it was written (Property 4).

Uncertainty in evaluation. Cluster-robust variance estimation [21, 28] and the bootstrap
[7] are the tools we use for intervals, following the argument that evaluation results should carry
error bars that account for the dependence structure of the data [23].


3     System Design
This section describes the arena concretely. Figure 1 shows the components; Figure 2 shows one
task’s passage through them.

3.1   Participants and objects
The arena has a roster of agents A, |A| = m. An agent is whatever sits behind the arena’s fixed
tool interface and turns an instruction into actions on the desktop: a single model under the
arena’s own scaffold (tool set, system prompt, step budget), or a multi-agent system with its
own planner, workers and verifier that the arena drives through the same interface and treats
as one entrant. The arena sees only the actions and the delivered result, so a single model
and a multi-agent system are rated by the same rule and can be compared on the same board.
Users submit tasks. A task τ is a natural-language instruction, optional file attachments, and an
optional starting URL. A battle b pairs one task with two distinct agents a, a′ ∈ A and produces
two runs, one per agent. A judgment is a user’s blind choice between the two runs of a battle.

3.2   Intake
Every task enters through one endpoint. The endpoint authenticates the submitter, checks that
the submitter’s consent to publication is current, classifies the message as a task (which will boot
two sandboxes) or as conversational text that should not, applies a near-duplicate guard against
the submitter’s recent tasks, and admits the task to a bounded queue. Admission is deliberately
wider than execution so that a burst of submissions becomes waiting time rather than an error.

3.3   Matchmaking
The two agents for a battle are drawn by a sampler that depends only on the roster, the count
of rated battles each agent has accumulated, and the current ratings. It depends on nothing the

                                                 3
submitter supplies. Three properties are enforced by construction and are stated here because
they matter for the rating analysis. Every eligible agent has a strictly positive probability in
every draw, so no agent can be starved. Agents with fewer rated battles are sampled more
often, with weight proportional to (na + κ)−1/2 for a pseudo-count κ > 0, so that measurement
converges toward equal exposure. Among opponents, pairs whose outcome is uncertain under
the current ratings are preferred, because those comparisons carry more information about the
parameters (Section 5.8).

3.4   Execution
Each run executes in its own sandboxed desktop environment: an isolated virtual machine with
a display, a browser, and a shell, provisioned fresh for the run. The two runs of a battle are
provisioned and started together, receive byte-identical inputs (instruction, attachments, tool
schemas, step budget, wall-clock budget), and execute concurrently. An agent acts through a
fixed tool set (pointer, keyboard, navigation, a screenshot on every step, and a bounded shell
where the environment permits it) and may end its run by delivering files and a final message.
Every step’s screenshot and action are recorded. Network egress from a sandbox is restricted to
public destinations; private address ranges are blocked at the resolver and at the proxy.

3.5   Judging
When both runs have ended, the battle becomes available for judging. A judge sees the task,
both trajectories as replays, and both final results, with the agents’ identities withheld by the
server until the judge has voted. The judge chooses one side, declares a tie, declares both
unacceptable, or abstains. A random fraction of battles, drawn at creation time, is assigned a
redundancy target of three judges rather than one; this sample is what agreement statistics are
computed from (Section 6.4). The submitter of a task may judge their own battle, blind like
anyone else; the treatment of that vote is specified in Section 5.5.

3.6   Rating and leaderboard
Two estimators run. A streaming update adjusts the two agents’ ratings the moment a judgment
resolves a battle (Algorithm 1). A batch estimator refits the pairwise model from every admissible
judgment on a fixed period and is what the public leaderboard displays, together with confidence
intervals and rank bands (Algorithms 2 and 3). Figure 3 shows, in a simulation, how the refit’s
interval narrows as judgments accumulate, and Figure 4 shows a simulated day of arrivals and
completed runs under the capacity model of Section 4.3. The leaderboard lists the roster only;
an agent removed from the roster keeps its historical battles in the corpus, and they continue to
inform the ratings of the agents it played, but it takes no position.

3.7   Failure to environment
A run that ends in failure (the agent gives up, the step or time budget is exhausted, or a checker
judges the delivered result wrong) is a candidate for conversion into a training environment: a
reproducible initial state, the instruction, and a grader derived from what went wrong (Figure 5).
The conversion runs as a pipeline with a stated latency target (Property 5).


4     Formal Model of Real-Time Evaluation
This section is the paper’s central contribution. We give a formal setting, then define real-time
as five properties. Each property has notation, a measurable quantity, an equation where one
applies, and a worked numerical example with clearly labeled illustrative inputs. We close with
a composite definition and a table of time-horizon tiers.

4.3      Property 2: live concurrent execution
Property 2 (Live concurrent execution) Both runs of a battle execute at the same time,
in isolated environments, on identical inputs, and execution is contemporaneous with submission.
Formally: (i) parity: the resolved input tuple I(b) (instruction, attachments, tool schemas, step
budget K, wall-clock budget W , environment image) is identical for both lanes; (ii) co-start: the
two lane start times differ by at most a skew bound ∆start ; (iii) isolation: the two environments
share no mutable state during [qb , eb ]; and (iv) contemporaneity: the machine latency to execution
end is bounded at a stated percentile,

4.4   Property 3: online rating updates
Property 3 (Online rating updates) The published rating at time t is a function of every
admissible judgment made before t − Lr , for a bounded update latency Lr that does not grow with
the size of the corpus. Define the staleness of the published rating at time t as

         ς(t) = t − min{ hb : hb ≤ t, b is not yet reflected in the rating served at t },     (10)

with ς(t) = 0 when no such judgment exists: the time the oldest unincorporated judgment has
been waiting. A board with no pending judgment is current, however long ago the last vote
arrived. The property requires supt ς(t) ≤ Hrate for a stated horizon.

    Two estimators satisfy this property in different ways (Section 5). The streaming update
touches two parameters per judgment and has latency of milliseconds, but it depends on the order
in which judgments arrived and cannot retroactively apply a retraction or a newly discovered
exclusion. The batch refit is order-independent and applies every rule to the whole corpus, at
the cost of a compute step. It runs on a fixed period ∆ with compute time c, so its staleness is
bounded by
                                         ς(t) ≤ ∆ + c.                                      (11)
The arena publishes the refit as the rating and shows the streaming value beside it, labeled,
because the streaming value is what a judge sees move when they vote.

Worked example (illustrative inputs). With ∆ = 30 s and c = 1 s, the served rating is
never more than 31 s stale. A benchmark that republishes weekly has ς up to 7×86,400 = 604,800
s, a ratio of about 2 × 104 . The streaming update, with a latency of the order of 10 ms, makes a
judge’s own vote visible to that judge at once; the refit makes it part of the published number
within ∆ + c.

4.6    Property 5: bounded feedback latency to a training environment
Property 5 (Bounded feedback latency) A failed run becomes a reusable, validated training
environment within a stated horizon. Let F be the set of runs whose outcome is a failure (the
agent gave up, exhausted its budget, or delivered a result a checker rejects). For u ∈ F with
end time eu , let εu be the derived environment and νu the time it is published, validated, to the
registry. The feedback latency is
                     Tuenv = νu − eu = Tucap + Tured + Tusyn + Tuval + Tupub ,                  (15)
the sum of capture, redaction, synthesis, validation, and publication stage times (Figure 5;
Algorithm 4). The property requires Tpenv ≤ Henv at a stated percentile, and it requires reusability:
εu must be reproducible from a stored initial state and a stored instruction, and validity: replaying
the failing trajectory in εu must reproduce the failure, and a reference trajectory must pass the
derived grader.

with a 20-minute wall-clock budget should expect T env of the order of an hour at its tail.

4.7   Composite definition and time-horizon tiers
Definition 4.1 (Real-time arena evaluation at horizon H) An arena evaluation is real-
time at machine horizon H and environment horizon Henv , at percentile p, if over its observation
window:

  1. (arrival) λ > 0 and Gmax (T ) ≤ H for every horizon T of at least one day;

  2. (execution) parity, co-start with ∆start ≤ H, and isolation hold for every battle, and
     (Lq + Lp + Le )p ≤ H;

  3. (rating) supt ς(t) ≤ H;

  4. (freshness) Ap ≤ H and cb = 0 for every rated battle;

  5. (feedback) Tpenv ≤ Henv , with reusability and validity.

The human latency Jb is reported alongside, at the same percentile, and is not part of the
definition, because it is the property of a population of judges rather than of the system.

   Table 1 arranges horizons into tiers. An evaluation can be real-time at one tier for some
properties and not others; the honest statement names the tier per property.

4.8    What the definition excludes
Three designs are sometimes described as real-time and fail Definition 4.1. A benchmark refreshed
on a schedule satisfies freshness at the refresh interval but fails arrival (its N (t) has epochs)
and fails rating staleness between refreshes. A platform that records tasks continuously but
executes them in nightly batches satisfies arrival and may satisfy contamination resistance, but
fails execution contemporaneity, and its judgments compare runs made under conditions that
may differ from the submitter’s. A platform that updates a streaming rating but publishes a
snapshot blended with a fixed benchmark score fails rating staleness for the published number,
because the blended component moves only when the snapshot is rebuilt.

5.5   Admissibility and evidence weight
Not every judged battle enters (18). A battle is excluded, in this order, when: the judge-visible
text named a model (the vote was not blind); one side has no run record; one side produced no
trajectory (an upstream outage, not a performance); the submitter ended one side early; the two
sides ran under different step budgets; or no admissible vote remains once retracted votes, votes
by judges marked untrusted, and votes recorded in less time than the two results take to read
are removed. Every exclusion is counted and published beside the rating.

if any independent judge voted, the submitter’s own vote is dropped from that battle’s consensus;
if none has, the submitter’s blind vote decides and the battle is counted in a published “self-judged

Rank bands. A rank is not a parameter, and its uncertainty is not a symmetric interval. We

it was first (Algorithm 3). Draws are seeded per agent so that the same corpus yields the same
band and adding an agent does not change another agent’s draws. The band uses each agent’s
marginal variance and ignores the off-diagonal covariance; this errs toward wider bands, which is
the safe direction for a published ordering.

5.7   Entry of a new agent
A new agent enters the roster with no rating. Until it has n0 = 30 rated battles it is provisional:
the refit’s estimate for it is withheld from the board, because a record with no loss, or no win,
is separated and its estimate is determined by the penalty rather than by data; the streaming
value is shown instead with an interval of the full scale, labeled as the streaming value. The
matchmaker samples the newcomer with weight (na + κ)−1/2 , κ = 4, so its exposure converges
to the field’s. Once the floor is reached, the fitted rating, its interval, and its rank band are
published. The agent is never given a seed rating that asserts it is average: its published number
is whatever its record implies.

6.1   Worked example: five agents, 211 votes
Table 2 gives a vote matrix for five agents, A to E, and the ratings it implies. Each cell of the
upper block records, for the row agent against the column agent, the counts (wins, losses, ties)
from the row agent’s point of view. Every vote is treated as a single admissible judgment by a
distinct judge with weight wb = 1, so the model-based interval (25) applies and the cluster-robust
interval coincides with it. Newton’s method from θ = 0 converged in five iterations at tolerance
10−10 with r = 10−3 ; the estimate was then centered on the mean of all five agents, since all
have at least n0 battles.
    Three features of the result are worth stating. The point estimates are ordered as the scores
are, which is expected when every agent has met every other with similar frequency. The
intervals of adjacent agents overlap: A (1073 to 1206) and B (988 to 1111) share the range 1073
to 1111, and the bootstrap accordingly gives A the band 1 to 2 rather than a bare first place.
And the ties, 29 of 211 votes, enter as half-wins and widen nothing in themselves; they carry
less information than decisive votes only through µb (1 − µb ) in (20), which does not depend
on yb . Had the same 211 votes been cast by three judges rather than 211, the cluster-robust
estimator (26) would have had G = 3 < m clusters, and no interval would have been published.

6.3   Arrivals and throughput in a simulation
Figure 4 shows one simulated day of the arrival and execution model of Properties 1 and 2: a
homogeneous Poisson arrival process at λ = 12 per hour, lognormal battle service times with
median 6 minutes and log-scale standard deviation 0.5, four concurrent execution slots served
first-in first-out, and seed 11. The day produced 280 arrivals, of which 279 battles (558 runs)
had completed by the end of the day; the mean queue wait was 0.09 minutes and the largest
2.87 minutes, consistent with the load ρ = 0.34 computed in Section 4.3. The cumulative-runs
curve stays close to twice the arrivals curve, which is the visual signature of contemporaneous
execution: work is completed at the rate it arrives, with a lag of one service time.

6.4   Vote quality
Consensus on a battle. When several judges vote on one battle, the outcome entering (18)
is the plurality choice, with the rule that a side wins only if it out-polls both the other side and
the non-preferences (ties and “both unacceptable”) combined; otherwise the battle is a tie. One
vote per person is counted, the earliest, so that a judge who voted under two identities does not
carry a majority alone.

Abstentions. A judge may decline to judge a battle. An abstention is recorded with its reason,
releases the judge’s hold so the battle returns to the queue, and does not enter the likelihood or
the agreement statistics. Abstention rates are published per reason because a high rate on a
class of tasks is information about the tasks.

7        Limitations
Human latency is not bounded by the system. Definition 4.1 excludes Jb on purpose,
and the illustrative timeline of Figure 2 makes it the dominant term. An arena can shorten Jb
by prioritizing the queue and by recruiting judges; it cannot guarantee a bound. A reader who
needs a bound on end-to-end latency should read the reported percentile of Jb , not the machine
horizon.

Judge population and self-judging. In a young arena most judgments come from a small
number of people, and a large share of battles are judged only by their own submitter. Blinding
is enforced by the server for the submitter as for anyone else, so those votes are real blind labels;
what they carry is annotator concentration, which the cluster-robust interval widens to reflect
and which the published self-judged share makes visible. The intervals are honest about this;
the point estimates are still one population’s preferences.

Task population. The tasks are whatever users submit. That is the property that makes the
evaluation track use, and it is also a selection effect that no reweighting in this paper corrects.
The published distribution over task categories is descriptive; a ranking on it does not transfer
to a workload with a different mix.

8       Conclusion
We have described an arena for computer-use agents and multi-agent systems in which real
tasks are executed by two entrants at once in identical isolated environments, judged blind, and
turned into a leaderboard. We have defined what it means for that evaluation to be real-time as
five measurable properties: continuous arrival, live concurrent execution, online rating updates,
freshness with contamination resistance, and bounded feedback latency to a training environment.
Each property has a quantity a deployed system can report at a percentile, and Definition 4.1
names the tier at which each holds. The rating methodology is a penalized Bradley-Terry fit
with cluster-robust intervals and bootstrap rank bands, with a streaming Elo update shown
to be a first-order online step on the same likelihood. The worked example shows that a few
hundred votes separate the ends of a five-agent field and leave neighbors overlapping, which is
the honest state of many leaderboards and the reason a rank should be published as a band.
The definitions are offered so that the word real-time, when applied to an evaluation, can be
checked rather than believed.

C.6    One battle, end to end
The following walks one battle through the system with the illustrative event times of Figure 2
and the ratings of Table 2. The two agents drawn are A and B.

  1. Submission (sb = 0). A user submits the first task of Table 4. Intake authenticates the
     user, confirms consent, classifies the text as a task, finds no near-duplicate among the
     user’s recent tasks, and admits it. Elapsed: under one second.

  2. Matchmaking and dequeue (qb = 5 s). The sampler draws Agents A and B. With 86
     and 87 rated battles they are the two agents with the most accumulated evidence, and
     the pairing is informative: σ(θ̂A − θ̂B ) = σ(0.804 − 0.288) = 0.626 is well inside the range
     where a comparison carries information. The battle waits 5 s for an execution slot.

  3. Provisioning and lane start (qb + δb = 45 s). Two isolated desktops are provisioned.
     Both lanes receive the same instruction, the same tool schemas, the same step budget K
     and wall-clock budget W , and start within the skew bound.

  4. Execution (eb = 6 min 45 s). Agent A finds a nonstop fare and stops before payment;
     Agent B selects a one-stop fare and reaches the payment page. Both runs end within the
     budgets. Every step’s screenshot and action are recorded for both.

  5. Judging (hb = 3 h 6 min 45 s). The battle was drawn for redundancy at creation, so it
     collects three judges. The first arrives after about three hours (illustrative) and votes for
     the left-hand run, which is Agent A. The two later judges also vote A; the consensus is A
     with three agreeing judges, and the battle contributes Pi = 1 to the agreement statistic of
     Section 6.4.

                                                        28
  6. Streaming update (within milliseconds of the first vote). Before the vote, RA =
     1139.7 and RB = 1050.0. By equation (22), the expected score of A is µ = 1/(1 +
     10(1050.0−1139.7)/400 ) = 1/(1 + 10−0.2243 ) = 0.6263. The factors from equation (23) are
     KA = 12 + 36 · 30/(30 + 86) = 21.31 and KB = 12 + 36 · 30/(30 + 87) = 21.23. With yb = 1
     and wb = 1, A gains KA (1 − µ) = 7.96 points and B loses KB (1 − µ) = 7.93 points: the
     streaming values become RA = 1147.7 and RB = 1042.1. The judge sees these move at
     once, labeled as the streaming value.

  7. Refit (within 31 s of the vote). The next periodic refit runs Algorithm 2 on the 212
     admissible battles. Adding one A-over-B outcome to the 211 of Table 2 moves the centered
     estimates to RA = 1142.6 (a change of +2.9) and RB = 1047.5 (a change of −2.5); the
     interval half-widths change by less than one Elo point. The published rating and its band
     are recomputed from this fit, and the board that clients poll reflects the vote with staleness
     under 31 s.

  8. Feedback (νu ≈ eb + 22 min, in parallel with judging). Agent B’s run ended with a
     constraint violation, so the pipeline of Section 4.6 captured, redacted, synthesized, validated
     and published the environment record of Figure 9 about 22 minutes after the run ended,
     well before the first judge arrived. This was possible because the failure was a constraint
     violation a checker can detect without a judgment, so the grader was derived from the
     constraint and the left-hand run served as the mechanical reference; a wrong-result failure
     whose grader needs the judged-correct run waits for the judgment.

    Two things in this walk-through are the point of the paper. The streaming update and the
refit agree in direction and differ in magnitude, because one is a single first-order step and the
other re-solves the whole likelihood; the board publishes the second and shows the first. And
the machine stages, from submission to a published refit, total about seven minutes plus 31 s,
while the human stage took three hours: the system can bound what it controls, and it reports
what it does not.
