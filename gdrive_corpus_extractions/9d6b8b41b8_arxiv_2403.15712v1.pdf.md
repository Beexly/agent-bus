The source is a multi-modal multiple-object-tracking paper, not a betting artifact. The derivation chain begins with the tracking objective on [PAGE 2]: “T ∗= arg max T P (T | O) . (1)”, where detections are \(O=\{O_1,\dots,O_T\}\), \(O_t=\{o^t_j\}\), and \(o^t_j=(b^t_j,t)\). The paper states the consistency requirement: “the ID assignment must be consistent and unique for the same instance in a video sequence” [PAGE 2]. Multi-hop, this probabilistic tracklet-set objective is then operationalized as a tracking-by-detection pipeline: a detector produces boxes, image patches are resized to \(256 \times 256\), LiDAR points are cropped to the box and converted to a \(256 \times 256\) BEV image [PAGE 3], two NAS-searched encoders produce modality features, and the fused feature is split into tracklet and detection features for correlation. The paper states the correlation difference as \(D_{n,m}=|f^{t-1}_n-f^t_m|\) [PAGE 3]. Those scores then feed an adjacency estimator that infers “new, end, confidence, and affinity scores” [PAGE 3], after which “we use the mixed integer programming (MIP) solver provided by Google OR-Tools 1 to find the optimal solution in the min-cost graph” [PAGE 3]. The gray-zone is that Eq. (1) is combinatorial over all tracklet sets; the paper does not give a closed-form posterior, nor a formal min-cost-flow objective, nor explicit score equations. It gives only the pipeline and solver. Thus the exact relaxation from \(P(T|O)\) to integer program is under-specified. A second gray-zone is sensor fusion: [PAGE 1] claims “Through a learned weighted feature fusion mechanism, the framework assigns greater significance to LiDAR point cloud features when cameras encounter difficulties or fail, and vice versa,” but [PAGE 3] says “we can get the feature encoding from each modality and then add them together to obtain the fused feature.” Addition is not the same as a learned adaptive weighting equation, and no fusion-weight equation, normalization, or sensor-dropout experiment is supplied. Therefore the robustness claim is plausible but not formally proven by the source. A third gray-zone is latency: [PAGE 3] gives \(Lat(\alpha)=\sum_{i=1}^{n}\alpha_i\cdot Lat(op_i)\), with table lookup. This is additive and assumes operation latencies are independent of scheduling, cache state, thermal throttling, and batch size. But [PAGE 7] says “the batch size we use is 1,” so the latency table is a batch-1, particular-device measurement, not a general real-time proof. A fourth gray-zone is the two-stage NAS: [PAGE 4] says “Pruning the low-weight operation will lead to a gap between the model from the first stage and the second stage,” and [PAGE 7] says “the structure of Stage II deviates slightly from that of Stage I.” Thus the searched architecture’s estimated latency may not equal deployed latency. A fifth gray-zone is evaluation: Table III reports validation MOTA 91.01 at \(\lambda=0.01\), while Table I reports test MOTA 89.59 for “Ours”; these are different splits and selection procedures, so the higher validation number cannot be treated as test performance. The paper also chose KITTI validation sequences 00, 02, 05, 07, 10, 11, 14, 16, 17, 18, and 19 because KITTI lacks an official validation split [PAGE 5]; repeated tuning against that split is a multi-week trap. Finally, the physical gray-zone: on Jetson Nano the paper reports 78 ms and 2 GB memory [PAGE 6], and search mode 2 uses 1913 MB [PAGE 7]. A nominal 2 GB device has little headroom after OS and runtime overhead, so the “under 80ms” and “can run on Jetson Nano” claims are margin-sensitive. The correct audit is therefore not “the model is real-time” but “the model is real-time under batch 1, measured sequence 19, measured device, measured memory, and unspecified thermal conditions.” That distinction is the core multi-hop derivation.

<SOURCE_OPERATORS_AND_EQUATIONS>
The paper’s formal tracking objective is given verbatim on [PAGE 2] as:
\[
T^{*}=\arg\max_{T} P(T\mid O).
\]
Here \(O\) is the set of detections across \(T\) frames, \(T=\{\tau_i\}\) is a set of tracklets, and \(P(T\mid O)\) is a conditional probability over tracklet sets. Units: probability is dimensionless; \(O\) and \(T\) are structured sets of detections and tracklets. Assumption: a unique and consistent ID assignment exists for each instance. Singularity/breakdown: if \(O=\varnothing\), the conditional probability is undefined without a prior; if detections are duplicated or ambiguous, the argmax is set-valued and not unique; if tracklet-set cardinality is not bounded, the search space is combinatorial. The paper does not give a closed-form posterior, so the exact solver gap is a formal gray zone.

The multi-objective NAS objective appears on [PAGE 4]:
\[
\min_{\alpha\in S,\theta}\left\{\mathbb{E}_{O,T\sim D_{\mathrm{val}}}\left[L(O,T\mid\theta,\alpha)\right]\right\},
\]
with
\[
L=L_{\mathrm{track}}+\lambda L_{\mathrm{latency}}.
\]
The paper also states: “Note that we set \(\lambda > 1\) since we mainly focus on reducing the latency in the first stage” [PAGE 4]. Units: \(L_{\mathrm{track}}\) is a tracking loss in nats or dimensionless negative log-likelihood-like units; \(L_{\mathrm{latency}}\) is a latency penalty in milliseconds if instantiated as \(Lat(\alpha)\); therefore \(\lambda\) must carry inverse-millisecond units for dimensional consistency, although the paper treats it as a scalar. Assumption: the loss is differentiable in \(\theta\) and the architecture parameters are relaxed. Singularity/breakdown: the objective is non-convex and the Pareto front need not be convex; if \(L_{\mathrm{latency}}\) is discontinuous because of hardware scheduling, the gradient-based relaxation is invalid; if \(\lambda\) is too large, accuracy is sacrificed; if \(\lambda\) is too small, the latency constraint is not met. The paper’s own Table III [PAGE 7] shows this trade-off: \(\lambda=10.0\) gives 6.2 ms and 89.42% MOTA, while \(\lambda=0.01\) gives 21.0 ms and 91.01% MOTA.

The two-stage search equations are:
\[
\alpha^{*}=\arg\min_{\alpha}\mathbb{E}_{O,T\sim D_{\mathrm{train}}}\left[L(O,T\mid\theta,\alpha)\right],
\]
\[
\min_{\theta}\mathbb{E}_{O,T\sim D_{\mathrm{val}}}\left[L_{\mathrm{track}}(O,T\mid\theta,\alpha^{*})\right],
\]
\[
\theta^{*}=\arg\min_{\theta}\mathbb{E}_{O,T\sim D_{\mathrm{train}}}\left[L(O,T\mid\theta,\alpha^{*})\right],
\quad \zeta^{*}=(\alpha^{*},\theta^{*}).
\]
These appear on [PAGE 4]. Units and assumptions: same as above, but the architecture is fixed in stage II and the latency constraint is removed: “In the second stage, the latency constraint is removed because the architecture will not be updated anymore” [PAGE 4]. Breakdown: the paper admits a stage gap: “Pruning the low-weight operation will lead to a gap between the model from the first stage and the second stage” [PAGE 4]. Also, the equations mix \(D_{\mathrm{val}}\) and \(D_{\mathrm{train}}\); the paper does not justify the distribution switch formally. If validation is used for architecture selection, test leakage is possible under repeated tuning.

The latency estimator is on [PAGE 3]:
\[
Lat(\alpha)=\sum_{i=1}^{n}\alpha_i\cdot Lat(op_i).
\]
Here \(Lat(op_i)\) is a measured average in milliseconds from a lookup table, and \(\alpha_i\) is a Softmax weight for operation \(op_i\). Units: milliseconds. Assumption: operation latency is additive and configuration-local. Breakdown: if the runtime fuses or schedules operations, the sum is not exact; if cache state, thermal throttling, or batch size changes, the table is stale; if an operation is not in the lookup table, the estimator is undefined. The paper’s own deployment data show the sensitivity: Jetson Nano 78 ms, Jetson Orin Nano 58 ms, GTX 1050 Ti 18 ms, GTX 2080 Ti 10 ms, Quadro RTX 6000 8 ms, Quadro RTX 8000 8 ms, TITAN RTX 9 ms, TITAN V 8 ms [PAGE 6].

The correlation operator is on [PAGE 3]:
\[
D_{n,m}=\left|f^{t-1}_{n}-f^{t}_{m}\right|.
\]
Units: same as the feature vector; if features are normalized, it is dimensionless. Assumption: absolute difference preserves affinity information. Breakdown: if \(N=0\) or \(M=0\), the matrix is empty; if features are misaligned or unnormalized, the difference is dominated by scale; if the encoder changes in stage II, the feature geometry shifts. The paper also uses birth/death hysteresis: “Only when the detection appeared in tbirth consecutive frames, the detection will be initialized” [PAGE 3], and “we check if they disappeared in tdeath frames” [PAGE 3]. The values of \(t_{\mathrm{birth}}\) and \(t_{\mathrm{death}}\) are not given, so the temporal logic is not reproducible from the source alone.

The paper’s headline numbers are not equations but are quantitative constraints: Table I reports “Ours” at MOTA 89.59, MOTP 85.44, IDSW 751, HOTA 67.32 [PAGE 6]. Table II reports Jetson Nano latency 78 ms with 2 GB memory [PAGE 6]. Table IV reports search mode 2 at 8 ms, MOTA 90.9, memory 1913 MB, versus mode 0 at 12 ms, MOTA 90.3, memory 2462 MB and mode 1 at 10 ms, MOTA 90.6, memory 2246 MB [PAGE 7]. These units are milliseconds, percent, and megabytes. The breakdown regime is therefore explicit: the latency constraint is not a single scalar guarantee; it is a device-, batch-, memory-, and sequence-dependent envelope.
</SOURCE_OPERATORS_AND_EQUATIONS>

<RETROCAUSAL_GENEALOGY>
The lineage is tracking-by-detection plus min-cost flow plus constrained NAS plus multi-modal fusion. The paper positions itself against “tracking-by-detection [35], [43] and joint-tracking-and-detection [9], [33], [34]” [PAGE 1] and adopts tracking-by-detection “due to its its inherent efficiency and proven effectiveness” [PAGE 1]. The min-cost-flow ancestry is explicit: “Following previous works [10], [16], [28], [43], MOT can be solved as a min-cost flow problem” [PAGE 3]. The NAS ancestry is DARTS: “The search space is adapted from DARTs [18] while modified to fit the MOT tasks” [PAGE 7], with candidate operations listed as “none, identity, 3 × 3, 5 × 5, 7 × 7 separable convolutions, 3 × 3, 5 × 5 dilated convolution, 3 × 3 max pooling, and 3 × 3 average pooling” [PAGE 7]. The constrained-NAS lineage runs through MNAS [31] and HardCoRe-NAS [22]: “Tan et al. [31] introduce latency constraints into the mobile neural architecture search (MNAS) approach” and “Nayman et al. [22] further strengthens the latency constraints and proposes the HardCoRe-NAS method” [PAGE 2]. The multi-modal lineage includes EagerMOT [15], mmMOT [43], and semantic-level fusion [41], with the paper’s own claim that fusion improves robustness but costs “significant latency and high energy consumption” [PAGE 1].

Retrocausally, the paper’s design choices explain its later weaknesses. Because it inherits DARTS, it inherits the pruning gap: “the structure of Stage II deviates slightly from that of Stage I” [PAGE 7]. Because it inherits tracking-by-detection, it inherits detector dependence: the Figure 2 caption says “Under the tracking-by-detection setting, Multi-object tracking can be regarded as a downstream detection task. It is hard to track dynamic objects under occlusion, which is common in real driving scenarios and significant for safe autonomous driving” [PAGE 4]. Because it inherits min-cost flow, it inherits combinatorial assignment and threshold sensitivity, but the paper does not publish \(t_{\mathrm{birth}}\) or \(t_{\mathrm{death}}\). Because it inherits multi-modal fusion, it inherits the missing stress test: no camera-dropout, LiDAR-dropout, rain, fog, glare, or thermal-soak experiment is reported, despite [PAGE 6] claiming robustness under “illumination, shadows, and occlusions” and [PAGE 1] claiming LiDAR “robustness in adverse weather conditions.”

Multi-week traps: first, validation-split overfitting. The paper uses KITTI sequences 00, 02, 05, 07, 10, 11, 14, 16, 17, 18, and 19 as validation and “the rest as the training dataset” [PAGE 5], then submits the best validation model to the test server. Repeatedly tuning \(\lambda\), search mode, and architecture against that split can inflate validation MOTA; indeed Table III reaches 91.01% validation MOTA [PAGE 7] while Table I reports 89.59% test MOTA [PAGE 6]. Second, latency-table overfitting: the paper measures “the average inference time” on sequence 19 [PAGE 5] and reports under-80 ms on Jetson Nano [PAGE 5], but a multi-week deployment will encounter thermal throttling, memory pressure, and batch-size changes; the table lookup does not model those. Third, fusion-claim overfitting: the learned weighted fusion is asserted on [PAGE 1] but not equationally specified; a multi-week trap is to assume sensor-failure robustness without a dropout test. Fourth, search-mode trap: Table IV shows mode 2 is best on latency, MOTA, and memory [PAGE 7], but this is on one search setup; treating it as universal ignores branch asymmetry and dataset shift. Fifth, evaluation-metric trap: MOTA alone can hide IDSW and fragmentation; Table I’s “Ours” has 751 IDSW and 276 Frag [PAGE 6], so a deployment that cares about identity continuity must audit those separately.
</RETROCAUSAL_GENEALOGY>

<RECURSIVE_THEORY_OF_MIND>
Crisis habit regression: the system’s intended crisis behavior is modality substitution. [PAGE 1] says the fusion “assigns greater significance to LiDAR point cloud features when cameras encounter difficulties or fail, and vice versa.” But the source does not give the weighting equation. The observable pipeline on [PAGE 3] says the encodings are added: “then add them together to obtain the fused feature.” If the learned weighting is not actually implemented as a dynamic gate, then under crisis the model regresses to a fixed-sum habit: a dead camera still contributes corrupt or zero features, and a dead LiDAR still contributes empty BEV features. That is the exact regression risk: the theory of mind says “the model will shift trust,” but the published operator description does not prove it. A second crisis habit is detector dependence: because the tracker is downstream of detection, a missed detection is not a tracking error the tracker can repair; it is an input veto. The Figure 2 caption’s “It is hard to track dynamic objects under occlusion” [PAGE 4] is an explicit admission.

Counter-trap: the opposite failure is over-teaching the model to expect failure. If one trains heavily on camera dropout, the model may learn to ignore camera texture even when the camera is healthy; if one trains heavily on LiDAR dropout, it may over-trust camera appearance and fail under glare or darkness. The paper gives no dropout curriculum, no modality-availability token, and no calibration test, so the counter-trap cannot be ruled out. A second counter-trap is latency over-constraint: setting \(\lambda=10.0\) yields 6.2 ms but 89.42% MOTA, while \(\lambda=0.01\) yields 21.0 ms but 91.01% MOTA [PAGE 7]. If the deployer overfits to the 80 ms edge limit, it may select a model that is unnecessarily weak on accuracy; if it overfits to accuracy, it may violate the real-time clock. The recursive theory of mind must therefore model the deployer’s own habit: “real-time” is not a property, it is a contract with a clock, a device, and a batch size.

Clock: the paper’s clocks are explicit. Jetson Nano 78 ms [PAGE 6] leaves only 2 ms to the 80 ms claim on [PAGE 2]. Quadro RTX 6000 is 8 ms [PAGE 6], but Table III’s \(\lambda=1.0\) model is 8.3 ms [PAGE 7], so a strict 8.0 ms budget would veto the higher-accuracy model. The birth/death logic is also a clock: “Only when the detection appeared in tbirth consecutive frames” [PAGE 3] and “we check if they disappeared in tdeath frames” [PAGE 3]. If \(t_{\mathrm{birth}}\) is too small, false detections become tracks; if too large, true objects are delayed. If \(t_{\mathrm{death}}\) is too small, tracks fragment; if too large, ghost tracks persist. The paper does not publish these values, so the recursive clock behavior is under-specified. The correct counter-trap is to make the clock explicit: measure p99 latency, not mean latency; measure memory headroom, not nominal capacity; and evaluate IDSW/Frag, not only MOTA.
</RECURSIVE_THEORY_OF_MIND>

<CROSS_LAYER_VETO_ADJUDICATION>
Physical-layer veto: the camera path is vetoed by illumination saturation, shadow, glare, and motion blur; the LiDAR path is vetoed by point sparsity at distance, adverse weather, and empty returns. The paper itself states the trade-off on [PAGE 1]: cameras “are susceptible to variations in lighting conditions,” while LiDAR excels at “3D geometry information” and “adverse weather conditions, yet with limitations on perceiving distant object detection owing to the sparsity of points.” That is a physical veto proof in the paper’s own words: neither modality is universally admissible. The fusion layer can only adjudicate if it has a real weighting mechanism. But [PAGE 3] says the encodings are added, and [PAGE 1] claims learned weighted fusion; the missing equation is the adjudication gap. Therefore the cross-layer claim “greater significance to LiDAR when cameras fail” is not proven by the source.

Biomechanical/mechanical-layer veto: the image patch is \(256\times256\) and the BEV is \(256\times256\) [PAGE 3]. Platform vibration, suspension jitter, rolling shutter, and motion blur can corrupt the image patch before the encoder sees it; LiDAR motion distortion can corrupt the BEV before the encoder sees it. The paper does not model ego-motion compensation, synchronization error, or vibration. A mechanical veto is therefore upstream of the NAS: if the patch is blurred, the searched cell cannot recover the lost texture. Similarly, the paper removes points outside the bounding box [PAGE 3]; if the detector box is wrong under occlusion, the LiDAR evidence is physically discarded before fusion. That is a detector-layer veto over the LiDAR layer.

Weather-layer veto: rain, fog, snow, and dust attenuate LiDAR and scatter camera light. The paper claims LiDAR robustness in adverse weather [PAGE 1] and shows qualitative “illumination, shadows, and occlusions” [PAGE 6], but it reports no weather-stratified quantitative table. A weather veto proof would require per-condition MOTA, IDSW, and detection recall; the source does not provide it. Thus the weather claim is a qualitative assertion, not an adjudicated proof.

Hardware-layer veto: Jetson Nano has 2 GB memory [PAGE 6]. Search mode 2 uses 1913 MB, mode 1 uses 2246 MB, mode 0 uses 2462 MB [PAGE 7]. The paper states: “The model trained from search mode 2 can run on Jetson Nano, while the other two cannot since the Jetson Nano only has a 2GB memory size” [PAGE 5]. That is a valid memory veto, but it is marginal: 1913 MB against a nominal 2 GB device leaves little room for OS, CUDA context, and input buffers. If actual free memory is below 1913 MB, even mode 2 is vetoed. Latency is similarly marginal: 78 ms against an 80 ms claim [PAGE 6]. A thermal soak or background process can push it over. Therefore the cross-layer adjudication must be: physical sensor vetoes are real; the paper’s fusion adjudication is under-specified; hardware vetoes are real and margin-sensitive; weather vetoes are unproven. The correct proof is a layered test matrix, not a single MOTA number.
</CROSS_LAYER_VETO_ADJUDICATION>

<RLVR_COUNTERFACTUAL_VETOES>
Scenario 1: LiDAR-dropout counterfactual. Take the published model and replace every LiDAR point cloud in KITTI sequence 19 with an empty point cloud so the BEV is all zeros. If the fusion is truly the “learned weighted feature fusion mechanism” claimed on [PAGE 1], the camera branch should remain admissible and the MOTA/IDSW degradation should be bounded. If the implementation is the additive fusion described on [PAGE 3]—“then add them together to obtain the fused feature”—empty LiDAR features can bias the fused vector and cause identity switches. Prediction: the dropout run will increase IDSW and Frag and decrease MOTA relative to Table I’s 89.59 MOTA, 751 IDSW, and 276 Frag [PAGE 6]. Verifiable veto criterion: if MOTA drops by more than a pre-registered margin or IDSW rises by more than a pre-registered fraction, the sensor-failure robustness claim is vetoed. This is a direct counterfactual because only the LiDAR input changes.

Scenario 2: Hard real-time counterfactual. On Quadro RTX 6000, Table III reports \(\lambda=1.0\) at 8.3 ms and 90.48% MOTA, while \(\lambda=10.0\) is 6.2 ms and 89.42% MOTA [PAGE 7]. Suppose the deployment contract is a hard 8.0 ms p99 budget, not mean latency. The higher-accuracy \(\lambda=1.0\) model is then inadmissible despite its better MOTA. Prediction: repeated measurement on sequence 19 with batch size 1, as stated on [PAGE 7], will show the \(\lambda=1.0\) model exceeding 8.0 ms on some runs, while \(\lambda=10.0\) remains below. Verifiable veto: if p99 latency exceeds 8.0 ms, the model is vetoed regardless of MOTA. This tests the paper’s own “below 80 milliseconds” claim [PAGE 2] at a tighter, device-specific clock.

Scenario 3: Edge-memory counterfactual. Table IV reports search mode 2 at 1913 MB, mode 1 at 2246 MB, and mode 0 at 2462 MB [PAGE 7]; Jetson Nano is 2 GB [PAGE 6]. The paper says mode 2 “can run on Jetson Nano, while the other two cannot” [PAGE 5]. Counterfactual: deploy on a Jetson Nano with a realistic OS/runtime footprint and measure peak resident memory. Prediction: mode 0 and mode 1 will fail allocation; mode 2 may fit only if free memory exceeds 1913 MB. Verifiable veto: if peak memory exceeds available memory, the model is vetoed even if MOTA is higher. This is a physical hardware veto, not an accuracy trade-off. A fourth optional check is the stage-gap counterfactual: because [PAGE 7] admits “the structure of Stage II deviates slightly from that of Stage I,” measured deployed latency should be compared to the stage-I estimated \(Lat(\alpha)\); if the measured value exceeds the constraint, the NAS search is vetoed. These scenarios are verifiable because they change one causal variable—sensor input, clock threshold, or memory ceiling—and predict an observable failure mode.
