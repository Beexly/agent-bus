<RETROCAUSAL_GENEALOGY>
The historical lineage of Dub sits at the intersection of three scientific/engineering traditions: link-attribution infrastructure, open-core dual licensing, and serverless OLAP analytics.

Link-management genealogy: Dub descends from Bitly (2008) and Rebrandly (branded short domains), inheriting the UTM/attribution paradigm originally built by Urchin Software and later absorbed into Google Analytics. [PAGE 1] explicitly positions Dub as replacing "Bitly, Rebrandly, PartnerStack light use, attribution spreadsheets, UTM chaos," which means GSE is adopting a consolidated attribution spine rather than inventing one. The scientific assumption is that branded short links plus conversion tracking create a closed loop from content exposure to paid-tier conversion.

Database and infra lineage: The self-host stack on [PAGE 1]—PlanetScale/MySQL, Tinybird/ClickHouse, Upstash Redis, R2/AWS storage—mirrors the modern serverless data-stack genealogy. Planetscale extends Vitess/MySQL; ClickHouse originated at Yandex circa 2016 as a columnar OLAP engine for clickstream; Tinybird productizes ClickHouse as managed infrastructure; Upstash provides serverless Redis; R2/AWS S3 provide object storage. This stack assumes that attribution events (clicks, referrals, conversions) are write-heavy, time-series, and analyzable in near-real time.

License lineage: AGPLv3 descends from GNU GPL with the Affero clause, which extends copyleft to software used over a network. The `ee/` open-core split on [PAGE 1] follows the GitLab/Elastic dual-license pattern: core under a strong copyleft, enterprise features under commercial terms. The critical genealogical insight is that AGPL's network-use trigger is non-standard compared to permissive MIT/Apache infrastructure; GSE cannot assume prior open-source handling patterns apply.

Multi-week traps: The scorecard on [PAGE 1] rates speed at only 5/10, yet leadership may compress the timeline. Trap 1: AGPL legal review (2–6 weeks) to determine whether internal dashboard use constitutes modification and whether cloud API usage avoids derivative-work status. Trap 3: OAuth and identity (1–2 weeks) for GitHub OAuth app creation, scope approval, and token rotation. The counter-trap creates a false sense of compliance that delays actual legal review until after code is written, making the eventual AGPL determination more expensive and more likely to require a rewrite.

Clock: The recursive clock is the race between integration readiness and legal clearance. If the founder cockpit demo is scheduled for week 3 but AGPL review is not complete until week 6, the team faces a forced choice: delay the demo (clock slip) or regress (copy code, bypass boundary). The clock is not merely a calendar; it is a governance pressure vessel. As \(t \to t_{\text{demo}}\), the probability of habit regression \(P_{\text{reg}}(t)\) increases monotonically unless the legal gate is already cleared. The only stable fixed point is to treat legal approval as a hard precondition, not a parallel workstream.

<CROSS_LAYER_VETO_ADJUDICATION>
Physical layer veto: The self-host stack spans six independent services: Vercel (edge), PlanetScale/MySQL (database), Tinybird/ClickHouse (analytics), Upstash Redis (caching/sessions), R2/AWS (object storage), and GitHub OAuth (identity). Veto condition: if any single region or service lacks a documented failover, and the system availability \(A_{\text{sys}}\) falls below 0.99, deployment is vetoed. Cloud-region outage, DNS failure, or OAuth provider outage are not exceptions; they are the nominal failure mode of a six-service chain and must be treated as weather-proof design constraints, not edge cases.

Biomechanical layer veto: Human factors govern founder cockpit inputs, operations workflow automation, and research-to-build packet conversion. Veto condition: if event taxonomy, data-boundary, and rollback docs are not written before package install [PAGE 1], the cognitive load of manual attribution mapping exceeds safe operating limits. Biomechanical failure modes include developer errors in link creation, mis-tagged conversion events, and silent data-boundary leaks between customer-facing and internal surfaces.

Weather veto proof: The system must remain vetoed under external shocks: (1) GitHub OAuth rate limiting or revocation; (2) Resend/Unsplash optional dependency changes or deprecation; (3) Dub Inc. changing pricing or gating previously open features behind `ee/`; (4) AGPL enforcement action against a network-exposed modification. The veto remains in force until rollback and migration paths are verified. This is weather-proof because it does not depend on fair-weather assumptions about upstream stability or vendor benevolence.
