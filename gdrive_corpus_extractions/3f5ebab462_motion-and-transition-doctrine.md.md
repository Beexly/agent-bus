Week 4 — The slot-machine crisis. A stakeholder will request an animated count-up or pulse on the Confidence Score Display to make the platform "feel live." The doctrine pre-empts this with a no-approval-path veto [PAGE 5], but only if the audit gate is enforced before the component reaches Level 2 maturity. <RECURSIVE_THEORY_OF_MIND>
Crisis habit regression, counter-trap, and the clock.

First-order belief of the engineer under pressure: "Animation equals polish; more smoothness equals higher perceived quality." This is the crisis habit regression. When deadlines compress, the engineer regresses to hardcoded CSS transitions, count-up number animations, and pulsing badges because these patterns are copied from consumer entertainment and gambling-adjacent interfaces where animation is used to manufacture excitement. The doctrine's second-order belief is the direct inverse: "Animation equals information; absence of animation means stable state; unearned animation is a brand liability" [PAGE 3].

The recursive theory of mind nests three actors:
1. The developer believes the reviewer will not inspect inline animation values.
2. The reviewer believes the developer has read the motion token system and uses `useReducedMotion()` in every Framer Motion component [PAGE 3].
3. The end user, seeing a pulsing confidence score, updates their brand prior from "calibrated analytics platform" to "slot machine / entertainment product" [PAGE 4].

This nesting creates a counter-trap. The design-token system is the first counter-trap: by forcing all animation values through CSS variables, it makes hidden magic numbers visible to computed-style audits. The motion review checklist is the second counter-trap: no component reaches Level 2 maturity without checkboxes for tokens, reduced motion, confidence-score stillness, and ease correctness [PAGE 5]. The Approval Gates table is the third counter-trap: adding animation to Confidence Score Display beyond opacity has no approval path, period [PAGE 5].

The clock variable is the maturity gate itself. Review must occur before Level 2 in the Component Maturity system [PAGE 5]. If the clock slips past component handoff, the veto changes character: it is no longer a pre-emptive design constraint but a post-facto refactoring order with O(n²) remediation cost because animated components are already consumed by downstream pages. The singularity is reached when a component ships to production with an animated confidence score and no reduced-motion fallback; at that point, the brand-inference damage to the user's model is already executed and cannot be rolled back by a CSS change alone.

Crisis regression is most likely when the product team confuses "live data indicator" (permitted pulse) with "data display value" (forbidden pulse) [PAGE 3]. The recursive defense is to require that any request for motion on a data field be answered with the information-theoretic question: what state change does this animation encode? If the answer is "none, it just looks active," the recursion bottoms out in a veto.

<CROSS_LAYER_VETO_ADJUDICATION>
Physical, biomechanical, and environmental veto proof.

Physical layer — GPU and frame budget. The display refresh interval at 60 Hz is Δt_frame = 16.67 ms. --duration-instant = 100 ms spans approximately six frames, above the perceptual threshold for a discrete micro-interaction. The token system favors opacity and transform animations (cheap GPU composite) over layout-triggering properties (height, width, top, left), which force main-thread reflow. A veto fires at the physical layer if any animation mutates layout properties during a user-triggered interaction, because the frame budget will be exceeded and jank will break the "instant-feeling" contract inherited from Linear.app [PAGE 1].

Biomechanical layer — Human perception and vestibular safety. The flicker-fusion threshold is roughly 50–90 Hz, but WCAG 2.3.1 imposes a hard regulatory veto at flashing frequency f > 3 Hz [PAGE 5]. The doctrine's table flags "Flashing or blinking (>3Hz)" as an accessibility violation [PAGE 5]. Vestibular safety forbids parallax on mobile scroll [PAGE 5] because conflicting motion between content and chrome can induce motion sickness in susceptible users. The star-field drift (individual stars translate ±2 px over 8–20 s [PAGE 4]) operates at angular velocities far below the vestibulo-ocular reflex threshold, so it is biomechanically safe as background; however, if a developer re-purposes that same drift on a foreground data value, the mismatch between expected and actual motion becomes a vestibular veto.

Environmental / "weather" veto proof. Although the product is software, "weather" here denotes ambient operating context. Bright ambient light reduces legibility of low-opacity layers; the Galaxy Background star field uses opacity 0.4–0.8 specifically to read as background, not foreground [PAGE 4]. In high-glare environments, that band drops below contrast threshold, so any dependency on the star field for spatial orientation is vetoed. Low-power mode and `prefers-reduced-motion` are environmental vetoes at the OS layer: if the global CSS rule for reduced motion is absent from the stylesheet [PAGE 5], the component violates the accessibility contract regardless of its internal elegance. The shimmer skeleton (background-position −200% → 200% over 1500 ms, linear, infinite while loading [PAGE 4]) is physically permissible only during loading; continuing it after data arrival would be a biomechanical and information-theoretic veto.

Adjudication matrix: a component is cleared for Level 2 only if all layers pass. Physical (frame budget, no layout thrashing), Biomechanical (f < 3 Hz, no parallax on mobile, no vestibular mismatch), and Environmental (reduced-motion respected, contrast sufficient in ambient context). Failure at any layer is an automatic veto; there is no trade-off clause that permits a 3 Hz flash if the easing is "beautiful."
</CROSS_LAYER_VETO_ADJUDICATION>
