<THINK_TRACE>
The source paper describes a computer-vision pipeline for football player tracking that is dominated by image segmentation, with tracking expressed as multipartite graph association and identity propagation. The first derivation hop is therefore the input data rate. The authors state that two static 4K cameras produce images of “an UHD (ultra high deﬁnition) of 3840 × 2160” at “the frame rate of 60 Hz”, and that the resulting pixel load is “995 328 000 pps” [PAGE 1]. This number is not merely contextual; it fixes the lower bound on computational work. If every pixel from every camera must be inspected at camera rate, the system must sustain approximately \(9.95328\times 10^8\) pixel inspections per second. In SI-like units, this is pixels per second, with the assumption that no region of interest is discarded before segmentation. The same page states the desired performance target indirectly: the paper reports “a speedup equal to 19.24 and a processing speed of 21.71 FPS with 128 threads” [PAGE 1]. However, the input camera rate is 60 Hz, so the achieved throughput is below the camera acquisition clock. The temporal mismatch is a central gray zone: the method improves over sequential processing, but it does not reach the native 60 FPS acquisition cadence.

The second derivation hop is the workload partition. The paper’s own tables show that segmentation, not graph tracking, consumes most of the sequential runtime. Table I reports for the 4K case: “Run time (s) 2267”, “Segmentation time (s) 2229”, and “Track time (s) 38” [PAGE 5]. The segmentation fraction is therefore approximately \(2229/2267 \approx 0.9832\), while tracking is approximately \(38/2267 \approx 0.0168\). This is confirmed by the authors’ own statement: “most of the execution time is spent on the segmentation part of the algorithm” [PAGE 5]. Any parallelization claim must therefore be evaluated primarily as a segmentation-parallelization claim. The tracking graph machinery is important for correctness, but it is not the dominant wall-clock consumer in the reported sequential baseline.

The third hop is the hybrid execution model. The paper proposes “a consumer-producer scheme to overlap the computing time of the two main procedures of the tracking algorithm: segmentation and tracking; as well a send and receive communication pattern to propagate the blob identities” [PAGE 1]. Algorithm 2 makes this explicit: even processes perform segmentation and “Send multipartite graph G from process pi to process pid+1”, while odd processes receive the graph and apply tracking [PAGE 3][PAGE 4]. This is a pipelined decomposition. In an idealized pipeline, the cycle time per batch is not the sum of producer and consumer times, but approximately the maximum of the stage times plus synchronization and communication overhead. The formal limit is therefore not “segmentation plus tracking” but “max(segmentation, tracking, communication) plus startup latency”. Since segmentation dominates the sequential baseline, the expected benefit of overlapping is limited unless segmentation itself is strongly parallelized inside each producer process. The paper indeed combines MPI with OpenMP: the cluster description says each processing node has “2 Intel Xeon E5-2650 running at 2.0 GHz for a total of 64 cores or 128 threads” and that “For each MPI process 2 OpenMP threads were enabled” [PAGE 5]. The hybrid model is therefore data parallelism inside segmentation plus task parallelism across producer-consumer stages.

The fourth hop is the graph-association model. The paper defines a multipartite graph with frame-layer nodes representing possible player blobs and weighted edges representing similarity: “the nodes are visualized as blobs that might or not correspond to football players, and the edges as the weighted value corresponding to the similarity between blobs” [PAGE 2]. The tracking procedure includes “Pruning the multipartite graph”, “Building a coincidence matrix”, “Forward analysis of borders for merge/occlusion events”, “Backward analysis of borders for split events”, and “Propagation of blob identities” [PAGE 4]. The computational scale of this graph layer depends on the number of graphs \(k\) and the number of nodes per graph \(n\). In the dense upper bound, each adjacent frame pair has \(n^2\) possible edges, so a \(k\)-layer graph has at most \((k-1)n^2\) adjacent-layer edges. If matching is performed per adjacent pair with a cubic bipartite assignment method, the operation count scales as \(\Theta((k-1)n^3)\). This is not a wall-clock equation; it is an operation-count scaling law. The wall-clock version depends on implementation, memory bandwidth, cache behavior, and whether pruning removes edges before matching. The paper’s Table IV varies multipartite graph size and shows that larger graphs can reduce tracking time: MPG size 20 gives “Track time (s) 2.07”, size 10 gives “14.19”, and size 5 gives “15.19” [PAGE 5]. The authors interpret this as reduced communication between adjacent nodes at the cost of greater memory use: “The growth of acceleration based on the size of the multipartite graph is probably due to a smaller amount of communications between adjacent nodes under the cost of a greater use of memory” [PAGE 5]. This is a crucial architectural trade-off: larger batches amortize communication and identity-propagation events, but they increase graph memory and potentially decrease numerical locality.

The fifth hop is the gray-zone audit of reported metrics. The paper defines speedup and efficiency as “S = Ts/Tp, and the efﬁciency as E = S/p” [PAGE 5]. If \(T_s\) is the sequential runtime and \(T_p\) is the parallel runtime, then speedup is dimensionless and efficiency is dimensionless per worker. The reported 128-thread case is internally consistent for speedup if \(T_s=2267\) s and \(T_p=117.85\) s: \(2267/117.85 \approx 19.24\). Efficiency follows as \(19.24/128 \approx 0.1503\), which matches the table’s “0.15” [PAGE 5]. However, several other rows are not internally consistent with the stated formula. For 32 threads, Table III gives run time “218.51” and speedup “14.45”, but \(2267/218.51 \approx 10.37\), not 14.45. For 16 threads, \(2267/426.27 \approx 5.32\), not the reported “7.41”. For 8 threads, \(2267/519.44 \approx 4.36\), not “6.23”. For 4 threads, \(2267/1215.93 \approx 1.86\), not “2.69”. For 2 threads, \(2267/2190.06 \approx 1.035\), not “1.49”. This does not invalidate the central 128-thread result, but it does mean that the scaling curve must be audited rather than accepted as a monotonic efficiency law. The paper itself says “there is a penalty in the efﬁciency” [PAGE 5], but the table’s nonmonotonic speedups suggest measurement, counting, or thread-mapping differences that need clarification.

A further gray zone is the frame count versus FPS. The paper states that the 4K video sequence has “a resolution of 3648×512, and 2877 frames of length” [PAGE 5]. If the 128-thread runtime is 117.85 s, then the implied FPS is \(2877/117.85 \approx 24.41\), not the reported “21.71” [PAGE 5]. Conversely, 21.71 FPS over 117.85 s implies about 2558 processed frames. This mismatch may arise from dropped frames, excluded warm-up frames, effective frame count after concatenation, or a different FPS accounting convention. It does not change the qualitative conclusion that the method is faster than sequential processing, but it changes the precision of the performance claim. The most defensible conclusion is not “21.71 FPS exactly for all 4K frames” but “the reported 128-thread configuration achieves roughly 22–24 FPS on the stated 4K test sequence, depending on frame-count accounting”.

The sixth hop is the real-time interpretation. The camera rate is 60 Hz [PAGE 1], so the acquisition frame interval is \(1/60 \approx 16.67\) ms. The reported processing speed of 21.71 FPS corresponds to approximately \(1/21.71 \approx 46.06\) ms per processed frame. Thus the pipeline is slower than the camera clock by a factor of approximately \(60/21.71 \approx 2.765\). The paper also notes that related work often fails to reach the desired processing time “equal or greater than 30 FPS” [PAGE 2]. The reported 21.71 FPS is therefore below both 60 FPS camera rate and the paper’s own cited 30 FPS threshold. This is a major operational constraint: the system is suitable for offline analysis or near-real-time review, but not for full-rate online tracking at the stated camera acquisition speed.

The final audit concerns physical consistency. The paper uses static cameras and a concatenated panorama, and it describes geometric transformation “which transforms the points in a trapezoid to points of a rectangle” [PAGE 5]. This implies a homography or projective mapping from image coordinates to field coordinates. The tracking graph includes “a kinematic model of constant speed” [PAGE 2], so the graph edge feasibility must respect player motion constraints. If a candidate association implies a displacement greater than what a human player can physically achieve between frames, the association should be vetoed. The source does not provide explicit maximum-speed thresholds, but the invariant is formal: in field coordinates, the displacement between consecutive frames must satisfy a bounded-speed inequality. Any claim of tracking under arbitrary occlusion, shadow, or weather must be tested against this physical veto. The graph can represent candidate identities, but it cannot create evidence when segmentation fails.

<SOURCE_OPERATORS_AND_EQUATIONS>
The paper’s main operators can be formalized without inventing new ratios. The first operator is pixel ingestion rate. Let \(N_c\) be the number of cameras, \(W\) the image width in pixels, \(H\) the image height in pixels, and \(f_s\) the sampling frequency in Hz. Then the raw pixel rate is

\[
R_{\text{pix}} = N_c W H f_s
\]

with units pixels \(\mathrm{s^{-1}}\). For the stated cameras, \(N_c=2\), \(W=3840\), \(H=2160\), and \(f_s=60\ \mathrm{Hz}\), giving

\[
R_{\text{pix}} = 2 \times 3840 \times 2160 \times 60 = 995\,328\,000\ \mathrm{pixels/s}.
\]

The source states: “the pixels per second (pps) to process in order to cope with the incoming information is of 995 328 000 pps” [PAGE 1]. This equation assumes every camera pixel is processed at camera rate and no compression or ROI reduction changes the count. It breaks down if the downstream concatenated video is cropped, downsampled, or subsampled. The paper’s later 4K test sequence is described as having “a resolution of 3648×512, and 2877 frames of length” [PAGE 5], which is not the same raster as the two-camera input. Therefore the camera-rate equation and the benchmark-throughput equation describe different workloads unless the transformation is explicitly accounted for.

The second operator is frame throughput. Let \(N_f\) be the number of processed frames and \(T_{\text{run}}\) the wall-clock runtime in seconds. Then

\[
\Phi = \frac{N_f}{T_{\text{run}}}
\]

with units frames \(\mathrm{s^{-1}}\). The paper reports “processing speed of 21.71 FPS with 128 threads” [PAGE 1]. If \(N_f=2877\) and \(T_{\text{run}}=117.85\ \mathrm{s}\), then

\[
\Phi = \frac{2877}{117.85} \approx 24.41\ \mathrm{FPS}.
\]

If instead \(\Phi=21.71\) and \(T_{\text{run}}=117.85\), then

\[
N_f = \Phi T_{\text{run}} \approx 21.71 \times 117.85 \approx 2558.5
\]

frames. The discrepancy is a source-level gray zone. The equation is exact, but the input count must be specified. The breakdown regime occurs when the reported FPS is computed from a different frame subset, such as excluding initialization, excluding I/O, or counting only tracked frames.

The third operator is speedup. The paper states: “The speedup was obtained as S = Ts/Tp, and the efﬁciency as E = S/p” [PAGE 5]. Formally,

\[
S(p) = \frac{T_s}{T_p}
\]

where \(T_s\) is sequential runtime, \(T_p\) is parallel runtime with \(p\) workers, and \(S\) is dimensionless. The efficiency is

\[
E(p) = \frac{S(p)}{p}
\]

also dimensionless. For the 128-thread row, \(T_s=2267\ \mathrm{s}\), \(T_p=117.85\ \mathrm{s}\), so

\[
S(128) = \frac{2267}{117.85} \approx 19.24,
\]

and

\[
E(128) = \frac{19.24}{128} \approx 0.1503.
\]

This matches Table III: “128”, “117.85”, “19.24”, “0.15”, “21.71”, “2.07” [PAGE 5]. The formal breakdown regime is any row where \(T_s/T_p\) does not equal the reported speedup. For example, with 32 threads, Table III gives \(T_p=218.51\) and reports \(S=14.45\), but

\[
\frac{2267}{218.51} \approx 10.37 \neq 14.45.
\]

Similar inconsistencies occur for 16, 8, 4, and 2 threads [PAGE 5]. Therefore the 128-thread claim is internally consistent, but the full scaling table requires clarification.

The fourth operator is an Amdahl-style effective serial fraction. This is not a new performance claim; it is an inversion of the reported efficiency under a simple parallel model. If

\[
E(p) = \frac{1}{1 + (p-1)f_s}
\]

where \(f_s\) is the fraction of runtime that behaves serially or non-scalably, then

\[
f_s = \frac{1/E - 1}{p-1}.
\]

For \(p=128\) and \(E=0.1503\),

\[
f_s \approx \frac{1/0.1503 - 1}{127} \approx 0.0445.
\]

For \(p=64\) and \(E=0.20\),

\[
f_s \approx \frac{1/0.20 - 1}{63} \approx 0.0635.
\]

The fact that the implied serial fraction changes across table rows indicates that the runtime is not governed by a single Amdahl serial fraction. Communication, memory bandwidth, thread affinity, MPI process mapping, and graph size are likely non-uniform contributors. The source itself notes: “The speedup appears to be linear inside a node, but when more nodes are used there is a penalty for the network communication” [PAGE 5].

The fifth operator is the graph-size scaling. Let \(k\) be the number of frame layers in the multipartite graph and \(n\) the number of candidate nodes per layer. The paper says: “A graph is k-partite if they can be partitioned into k disjoint independent sets” and that nodes are blobs while edges are similarity values [PAGE 2]. For adjacent-layer association, the dense upper bound on candidate edges is

\[
|E_{\text{adj}}| \le (k-1)n^2.
\]

If each adjacent-layer association is solved by a dense bipartite matching algorithm with cubic scaling, the operation count is

\[
C_{\text{match}} = \Theta((k-1)n^3).
\]

The units are elementary operations, not seconds. The wall-clock version requires an implementation cost per operation and memory-access cost. For \(k=20\) and \(n=20\), the dense adjacent-edge upper bound is

\[
(20-1)\times 20^2 = 7600
\]

candidate edges, and the cubic matching unit bound is

\[
(20-1)\times 20^3 = 152\,000
\]

operation units. This is consistent with the paper’s observation that larger multipartite graphs can improve tracking time: Table IV reports MPG size 20 with track time “2.07” s, MPG size 10 with “14.19” s, and MPG size 5 with “15.19” s [PAGE 5]. The formal explanation is batch amortization: more candidate context per graph can reduce the number of cross-graph identity-propagation events and communication rounds. The breakdown regime is memory pressure. The paper warns: “caution should be taken with the size of the graph in terms of memory consumption” [PAGE 5].

If each edge stores a scalar weight, the adjacency memory is approximately

\[
M_{\text{edge}} = b_e (k-1)n^2
\]

where \(b_e\) is bytes per edge. If each edge stores a \(d\)-dimensional feature vector in 32-bit floating point, then

\[
M_{\text{edge}} = 4 d (k-1)n^2
\]

with units bytes. For \(k=20\), \(n=20\), \(d=10\), and float32 features,

\[
M_{\text{edge}} = 4 \times 10 \times 7600 = 304\,000\ \text{bytes} \approx 0.304\ \text{MiB}.
\]

If all frame pairs, not only adjacent pairs, are considered, the upper bound becomes

\[
|E_{\text{all}}| \le \binom{k}{2} n^2,
\]

which for \(k=20\), \(n=20\) gives

\[
\binom{20}{2} \times 400 = 190 \times 400 = 76\,000
\]

edges. The paper’s matching and identity propagation are described between adjacent graphs and across neighboring processes, but the general graph-pruning stage may consider broader relationships [PAGE 4]. Therefore the memory equation is workload-dependent. The exact breakdown occurs when graph allocation exceeds node RAM, when cache misses dominate matching, or when MPI message volume saturates the network.

The sixth operator is communication cost. The paper’s producer-consumer pattern sends graphs between processes: “Send multipartite graph G from process pi to process pid+1” [PAGE 3]. Additional sends occur between odd processes to propagate identities: “Send graph G of frame fo from process pid to pid+2” [PAGE 4]. Let \(Q\) be the serialized graph size in bytes, \(B\) the effective network bandwidth in bytes per second, and \(\lambda\) the per-message latency in seconds. A first-order communication time is

\[
T_{\text{comm}} = \frac{Q}{B} + \lambda.
\]

If there are \(m\) messages, then

\[
T_{\text{comm,total}} = m\left(\frac{Q}{B} + \lambda\right)
\]

under a non-overlapped assumption. With overlap, the effective added time is closer to the maximum of communication and computation on the critical path, not the sum. The source notes a network topology with bonded interfaces and Lustre storage to support parallel reads [PAGE 5], but it also notes a network penalty when more nodes are used [PAGE 5]. The breakdown regime is message-count explosion: if graph size \(k\) increases while the number of processes increases, the number of send/receive events can grow faster than bandwidth can absorb.

The seventh operator is the tracking pipeline cycle time. Let \(T_\sigma\) be segmentation time per batch, \(T_\tau\) tracking time per batch, and \(T_{\text{sync}}\) synchronization plus communication overhead. In a perfectly overlapped consumer-producer pipeline,

\[
T_{\text{cycle}} = \max(T_\sigma, T_\tau, T_{\text{sync}}) + T_{\text{startup}}.
\]

Without overlap,

\[
T_{\text{cycle,seq}} = T_\sigma + T_\tau + T_{\text{sync}}.
\]

The source states the goal: “consumer-producer scheme to overlap the computing time of the two main procedures of the tracking algorithm: segmentation and tracking” [PAGE 1]. Because Table I shows segmentation time “2229” s versus track time “38” s for 4K [PAGE 5], the pipeline’s theoretical gain from overlap alone is bounded by the ratio of the smaller stage to the larger stage. If \(T_\sigma \gg T_\tau\), then

\[
\frac{T_{\text{cycle,seq}}}{T_{\text{cycle}}}
\approx
\frac{T_\sigma + T_\tau}{\max(T_\sigma,T_\tau)}
=
1 + \frac{T_\tau}{T_\sigma}.
\]

Using the 4K values,

\[
1 + \frac{38}{2229} \approx 1.017.
\]

Thus overlap alone cannot explain the observed 19.24 speedup. The dominant gain must come from parallelizing segmentation itself, not merely from hiding tracking behind segmentation.

The eighth operator is real-time clock feasibility. Let \(f_{\text{cam}}\) be camera frame rate and \(\Phi\) the tracker output frame rate. Real-time processing requires

\[
\Phi \ge f_{\text{cam}}.
\]

For \(f_{\text{cam}}=60\ \mathrm{Hz}\), the frame interval is

\[
\Delta t = \frac{1}{60} \approx 0.01667\ \mathrm{s}.
\]

The reported 21.71 FPS gives

\[
\Delta t_{\text{proc}} = \frac{1}{21.71} \approx 0.04606\ \mathrm{s}.
\]

The clock deficit factor is

\[
\frac{f_{\text{cam}}}{\Phi} = \frac{60}{21.71} \approx 2.765.
\]

The breakdown regime is exact: if \(\Phi < f_{\text{cam}}\), the system cannot track every acquired frame in real time. The paper’s related-work discussion mentions a desired processing time “equal or greater than 30 FPS” [PAGE 2], and the reported 21.71 FPS is below that threshold.

The ninth operator is physical motion feasibility. Let \((X_t,Y_t)\) be field coordinates in meters at time \(t\), and let \(v_{\max}\) be a maximum plausible player speed in meters per second. For consecutive frames with interval \(\Delta t\), a physically valid association should satisfy

\[
\left\|(X_{t+1}-X_t,\ Y_{t+1}-Y_t)\right\|_2
\le v_{\max}\Delta t + \epsilon,
\]

where \(\epsilon\) is localization uncertainty in meters. The paper’s nodes use “a kinematic model of constant speed” [PAGE 2], and the camera geometry uses a trapezoid-to-rectangle transformation [PAGE 5]. If the image-to-field transform is \(H\), then image coordinates \((u,v)\) map to field coordinates by a projective relation. The formal breakdown occurs if \(H\) is ill-conditioned, if players leave the calibrated trapezoid, or if shadows and rain violate the segmentation assumptions. The graph can prune impossible edges, but it cannot recover identity when the segmentation stage produces no reliable blob.
</SOURCE_OPERATORS_AND_EQUATIONS>

<RETROCAUSAL_GENEALOGY>
The paper belongs to a lineage that moves from classical low-level football image analysis to graph-based multi-object tracking and then to high-performance computing. The earliest referenced method is Lefèvre et al., described as “a method based on a fast snake” with “a processing time of 2 seconds per frame” on low-resolution Matlab input [PAGE 2]. That lineage treats tracking as contour deformation. The present paper instead treats identity association as a graph problem: “A graph is k-partite if they can be partitioned into k disjoint independent sets” [PAGE 2]. The nodes are candidate blobs, and the edges are similarity relations across frames [PAGE 2]. This is a shift from contour-based tracking to combinatorial data association.

A second lineage is the network-flow and multi-target association tradition. The paper cites Shitrit et al., where “they use a network flow formulation as a linear programming optimization problem” and report “3.95 FPS” on a single core [PAGE 2]. That lineage treats tracking as global optimization over detection hypotheses. The present work is related but not identical: it uses multipartite graphs, forward and backward border analysis, and identity propagation between batches [PAGE 4]. The key historical trap is assuming that a more expressive graph model automatically solves occlusion. The paper’s own segmentation stage shows that most runtime is spent before graph matching even begins [PAGE 5]. Therefore the lineage from graph theory to tracking must be mediated by detection quality and pixel processing throughput.

A third lineage is the parallelization lineage. The authors’ prior work parallelized spatial segmentation with OpenMP and reported “a speedup factor of 4 and efﬁciency of 0.1 with 8 threads” on standard-definition videos [PAGE 2]. The present paper generalizes that effort into a hybrid MPI/OpenMP design. The historical progression is: Matlab prototyping, then C++/OpenCV implementation, then multi-threading, then distributed-memory MPI, then producer-consumer overlap. The multi-week trap is to optimize the tracking graph while ignoring the fact that segmentation is the bottleneck. The paper explicitly avoids that trap by stating: “the segmentation section is the bottle neck of the algorithm requiring heavy computational power” [PAGE 5]. However, a deeper trap remains: benchmark scaling can be confounded by frame-count accounting, thread mapping, and network communication. The reported table is not uniformly self-consistent, so the genealogical lesson is that parallel tracking claims must be audited at the level of workload definition, not merely at the level of headline speedup.
</RETROCAUSAL_GENEALOGY>

<RECURSIVE_THEORY_OF_MIND>
The tracker must model the intentions and physical constraints of players while simultaneously modeling its own failure modes. The paper’s graph includes “a kinematic model of constant speed” as part of the node characteristics [PAGE 2]. This is a predictive assumption: a player’s next position is expected to be compatible with prior motion. Under normal play, this assumption reduces the association space. Under crisis conditions—occlusion, sudden direction changes, congestion around the ball, rain, light changes, or stadium shadows—the constant-speed assumption can become brittle. The paper acknowledges these difficulties: players “look quite similar among those belonging to the same team” and often create “multiple occlusions” [PAGE 1]. It also notes external factors such as “rain, light changes, and stadium’ shadows” [PAGE 1].

A recursive theory of mind for this system has three layers. The first layer is the physical player model. Players cannot teleport, cannot exceed plausible speed limits, and cannot occupy impossible positions on the field. The graph should therefore treat associations as hypotheses constrained by motion continuity. The second layer is the tracker’s self-model. The tracker knows that its input is a concatenated 4K video from static cameras [PAGE 1][PAGE 5], but it also knows that segmentation may fail when green regions, field lines, shadows, or uniforms confuse the segmentation pipeline. The third layer is the temporal clock. The camera runs at 60 Hz [PAGE 1], while the reported processing speed is 21.71 FPS [PAGE 1]. The tracker’s “belief” about each player becomes stale between processed frames. If the system assumes that identity propagation remains valid across long gaps, it may carry forward incorrect identities during occlusions.

The crisis habit regression is the tendency to fall back to simplistic association when evidence is weak: for example, choosing the nearest blob or preserving identity by inertia. This habit is dangerous because it can propagate a wrong identity through a merge/split event. The paper’s counter-trap is the multipartite graph’s explicit handling of such events: “Forward analysis of borders for merge/occlusion events” and “Backward analysis of borders for split events” [PAGE 4]. These operators allow the system to reconsider identities when blobs merge or split, rather than blindly continuing a track. The counter-trap also includes pruning based on multiple descriptors: “histogram, position, shape, area and speed” [PAGE 4]. This reduces reliance on a single fragile cue.

The clock trap is distinct from the perceptual trap. Even if the graph is correct, the system may be too slow for real-time operation. The source states the camera rate and the pixel load [PAGE 1], and the achieved FPS is below the camera rate. The recursive consequence is that the tracker’s internal model must support delayed decisions: it may need to process batches, propagate identities after the fact, and tolerate latency. The paper’s batch mode and multipartite graph size reflect this: larger graphs can reduce communication overhead and improve tracking time, but they increase memory pressure [PAGE 5]. The optimal recursive policy is therefore not “track every frame instantly” but “maintain graph consistency under bounded latency and bounded memory”.
</RECURSIVE_THEORY_OF_MIND>

<CROSS_LAYER_VETO_ADJUDICATION>
The strongest veto comes from the physical layer. Football players are biomechanical agents with bounded speed and acceleration. If the tracker proposes an association that requires a player to move faster than physically possible, the association must be rejected. Let field coordinates be in meters, time in seconds, and maximum plausible player speed be \(v_{\max}\) in meters per second. For frame interval \(\Delta t\), the hard inequality is

\[
\| \mathbf{x}_{t+1} - \mathbf{x}_t \|_2 \le v_{\max}\Delta t + \epsilon.
\]

If \(\epsilon\) is localization uncertainty in meters, then an association outside this bound is physically inadmissible. This veto operates even if the graph edge has high appearance similarity, because appearance similarity cannot override biomechanical impossibility. The paper’s nodes include position from “a kinematic model of constant speed” [PAGE 2], but the source does not provide an explicit \(v_{\max}\). Therefore the veto must be parameterized. If \(v_{\max}=10\ \mathrm{m/s}\) and \(\Delta t=1/60\ \mathrm{s}\), the maximum plausible field displacement is approximately \(0.167\ \mathrm{m}\) before uncertainty. In image coordinates, this threshold must be transformed through the camera geometry. The paper’s trapezoid-to-rectangle transformation [PAGE 5] provides the geometric basis for such a mapping, but the exact calibration parameters are not given in the excerpt.

The second veto comes from segmentation evidence. If the segmentation stage produces no reliable contour for a player, the tracking graph cannot assign a valid node. The paper’s segmentation pipeline includes HSV conversion, normalized local spatial variance, green-region identification, edge detection, Hough line removal, morphology, and circularity filtering [PAGE 3]. These steps are vulnerable to rain, shadows, and light changes [PAGE 1]. A formal veto is: if the detection likelihood for a player is below the graph’s pruning threshold, identity propagation must not assert a confident track. In information-theoretic terms, the tracker cannot increase certainty about a player’s identity when the observation channel has lost the player. The graph can maintain a hypothesis, but it cannot certify identity without evidence.

The third veto comes from the clock layer. The camera rate is 60 Hz, giving a frame interval of \(16.67\ \mathrm{ms}\) [PAGE 1]. The reported processing speed is 21.71 FPS, corresponding to \(46.06\ \mathrm{ms}\) per processed frame [PAGE 1]. If the application requires online tracking at camera rate, the system fails the real-time veto. If the application is offline analysis, the veto is relaxed, but the latency still affects downstream semantic analysis. The paper’s architecture is part of “ACE, a larger system” for football analysis [PAGE 1], so delayed tracking may be acceptable if the final product is annotation rather than live control.

The fourth veto comes from network and memory layers. The paper states that when more nodes are used, “there is a penalty for the network communication” [PAGE 5], and it warns about graph memory consumption [PAGE 5]. If increasing multipartite graph size improves tracking time but causes memory allocation failure or network saturation, the larger-graph policy is vetoed. The cross-layer adjudication is therefore hierarchical: physical impossibility vetoes first, missing segmentation evidence vetoes second, real-time clock infeasibility vetoes third for online use, and memory/network constraints veto implementation choices that cannot be sustained on the target cluster.
</CROSS_LAYER_VETO_ADJUDICATION>

<RLVR_COUNTERFACTUAL_VETOES>
The first verifiable counterfactual veto concerns multipartite graph size. The paper reports that increasing MPG size from 5 to 10 to 20 reduces run time and improves FPS: MPG size 20 gives “117.85” s run time and “21.71” FPS, size 10 gives “164.27” s and “15.58” FPS, and size 5 gives “217.96” s and “11.74” FPS [PAGE 5]. The authors explain this as reduced communication between adjacent nodes at the cost of memory [PAGE 5]. The verifiable prediction is: if memory bandwidth and capacity are not limiting, increasing MPG size should reduce or stabilize tracking time while increasing graph memory. The veto scenario is: if MPG size 20 causes memory allocation failure, cache thrashing, or network congestion on the target cluster, the observed improvement should disappear or reverse. A concrete RLVR check is to measure peak resident memory and network message count for MPG sizes 5, 10, and 20 at fixed 128 threads. If MPG size 20 produces higher runtime than MPG size 10 under the same memory and network conditions, the memory-saving claim is vetoed.

The second verifiable counterfactual veto concerns thread scaling. Table III reports that increasing threads from 1 to 128 reduces run time from “2267.00” s to “117.85” s and increases speedup to “19.24” [PAGE 5]. The verifiable prediction is: if the workload is sufficiently parallel and the cluster mapping is stable, adding threads should not increase wall-clock time. The veto scenario is: if adding threads causes run time to increase due to lock contention, MPI process oversubscription, or OpenMP affinity violations, the scaling claim is vetoed. A concrete RLVR check is to rerun the 128-thread configuration with the same process-to-core mapping and measure run time variance. If the 128-thread run time becomes greater than the 64-thread run time of “176.69” s under the same video and graph settings, the monotonic scaling claim fails. The table already contains smaller-scale inconsistencies: for 32 threads, \(2267/218.51 \approx 10.37\), not the reported speedup “14.45” [PAGE 5]. That does not veto the 128-thread result, but it does veto any unqualified claim that all table rows follow a single scaling law.

The third verifiable counterfactual veto concerns resolution reduction. Table V reports that at 128 threads, 4K run time is “117.85” s, FHD run time is “31.10” s, and HD run time is “17.71” s [PAGE 5]. If the number of frames and the processing pipeline are held constant, lower pixel count should reduce segmentation time. The verifiable prediction is: run time should decrease approximately in proportion to processed pixel count, after accounting for fixed I/O and graph overhead. The veto scenario is: if FHD or HD run times do not decrease with pixel count, or if the reported speedups are not consistent with the sequential baselines, then the resolution claim is invalid. Using Table I, the sequential baselines are “542” s for FHD and “286” s for HD [PAGE 5]. With the reported parallel times, the direct speedups are \(542/31.10 \approx 17.43\) and \(286/17.71 \approx 16.15\), not the reported “24.15” and “23.99” [PAGE 5]. The formal veto is therefore active unless the paper clarifies whether the speedup denominators differ from Table I, whether frame counts differ by resolution, or whether the sequential baseline was rerun under different conditions. A concrete RLVR check is to process the same frame count at 4K, FHD, and HD with identical batch size and graph size, then verify that \(S = T_s/T_p\) matches the reported speedup for every resolution.
</RLVR_COUNTERFACTUAL_VETOES>
