A data-refresh job scheduled every hour that fails at 02:00 will not retry until the next cycle at 03:00, leaving the board stale for up to the full inter-arrival interval. Over a week of undetected worker failure, the "no stale data" invariant is violated continuously without a hard exception.

Third, sports-analytics calibration tradition (confidence scores calibrated against historical results, versioned and auditable picks) derives from forecasting and proper-scoring-rule literature. The trap is milestone inversion: the pricing ladder requires verified milestones (e.g., settled-pick counts and calibration thresholds) before stepping up from FOUNDING to PROVEN. If the team publishes calibration metrics before the underlying settled-pick population reaches the milestone, the evidence base is retrospectively constructed. Because each pick carries model_version and generated_at, an audit would reveal the temporal inversion, but only after subscribers have upgraded on false premises.

Fourth, legal-scraping tradition (hiQ Labs v. LinkedIn public-data boundaries, CFAA constraints, GDPR privacy review) informs the Scraping Clearance Engine. The trap here is scope creep: scores24.live is classified as permission_required, allowing manual UX research but forbidding automation without written consent from Kiito OÜ. A developer under deadline pressure may write a "research script" that gradually transitions from manual UX review to automated data capture, slipping across the clearance boundary. Because wrapExtractedRecord() throws if clearance is not granted, the failure mode is a thrown exception at job runtime, but the preceding un-cleared extraction may already have occurred in a local or staging environment, creating a rights-snapshot gap that is difficult to retroactively remediate.
</RETROCAUSAL_GENEALOGY>

<RECURSIVE_THEORY_OF_MIND>
This section models the operators' beliefs about the system, the system's model of the operators, and the recursive loop between them under crisis conditions.

Crisis habit regression: When an incident occurs (stale data, failed webhook, clearance exception), individual developers regress to forbidden local optima. The documented non-negotiable rules are precisely the habits most likely to be abandoned under pressure: no frontend-only paywalls (rule 3) is violated by adding a client-side "if premium show pick" guard; no secrets in code (rule 4) is violated by temporarily hardcoding a Stripe key to debug a webhook; no stale data (rule 5) is violated by serving cached results while the ingestion API is down; tests required (rule 6) is violated by shipping a hotfix without Vitest coverage; types required (rule 7) is violated by casting to any to unblock a typecheck error. These regressions are locally rational (they restore service quickly) but globally destructive because they erode the invariant stack that makes the platform auditable.

Counter-trap: The recursive counter-trap is to make regression structurally more expensive than compliance. CI/CD pipelines enforce `npm run test`, `npm run typecheck`, and `npm run lint` before merge. Startup env-validation asserts NEXTAUTH_URL equals NEXT_PUBLIC_APP_URL and that required Stripe price IDs are present. The Scraping Clearance Engine is invoked at job startup, not inside the extraction loop, so a developer cannot "comment out" the check for one source without disabling the whole job. These are not mere guidelines; they are compilation-time and deployment-time gates that force the operator to confront the invariant before the system runs.

Clock: The BullMQ job scheduler defines the maximum staleness horizon. If the data-refresh job interval is \Delta t_{\text{job}}, then undetected freshness failure persists for at most \Delta t_{\text{job}} before the next attempt. However, if the job itself fails silently (worker crash without retry configuration), the effective horizon extends to operator mean-time-to-detection, which can be days. The Stripe webhook retry window \Delta t_{\text{retry}} creates a second clock: entitlement divergence cannot self-heal faster than Stripe's retry cadence. The recursive problem is that operators model users as rational subscribers, while users model the platform as trustworthy. Under crisis, if operators hide failures (regression), users update their trust model downward, increasing churn, which further pressures operators to cut corners — a second-order feedback loop that the CI/CD gates are designed to break.
</RECURSIVE_THEORY_OF_MIND>

<CROSS_LAYER_VETO_ADJUDICATION>
Physical-layer vetoes: The platform runs on Docker containers. A host-level OOM kill or datacenter power event removes the Node.js process and Redis instance simultaneously. If Redis loses persistence (AOF/RDB misconfiguration), BullMQ queues are flushed; in-flight data-refresh and picks-generation jobs are lost. Veto proof: the system must degrade to a read-only or maintenance state rather than serve stale picks, because rule 5 forbids stale data and rule 1 forbids fake data. There is no graceful degradation path that fabricates picks; the veto is total service suspension for affected sports until ingestion is restored.

Network-layer vetoes: The Odds API is the licensed sports-data source. If it returns non-2xx responses, rate-limits, or changes its schema, the data-ingestion-agent receives no structured line data. Because the prediction engine's source of truth is structured odds/line data, a missing source forces a hard stop of pick generation for the affected fixtures. Veto proof: no fallback to scraped or fabricated data is permitted. The apex-to-www DNS redirect and NEXTAUTH_URL/NEXT_PUBLIC_APP_URL parity are network identity conditions; if mismatched, Google OAuth fails and users cannot authenticate, which is a veto on the subscription and entitlement layer independent of application logic.

Compute-layer vetoes: Claude API is used for content generation only. If the Anthropic API is slow or returns malformed content, editorial wraps fail, but structured picks remain servable because predictions do not depend on Claude output. However, if local content-assembly code blocks the Node.js event loop (synchronous file I/O, heavy JSON transformation), the API routes become unresponsive. Veto proof: content generation must remain strictly asynchronous and isolated; a blocked event loop is a compute veto that takes down the entire web process, not just the content feature.

Data-layer vetoes: PostgreSQL connection-pool exhaustion under concurrent Prisma migrations and web traffic creates a write lock. If a migration holds an exclusive lock, new picks cannot be inserted, versioned, or audited. Veto proof: migrations must be online and non-blocking, or deploys must be scheduled during low-traffic windows; otherwise the auditability invariant (all picks versioned and auditable) is violated by insertion failure.

Biomechanical and weather analogs: Literal biomechanics and atmospheric weather do not apply to a pure software platform with no athlete, venue, or outdoor component. The biomechanical analog is operator cognitive load and CI pipeline friction; the weather analog is external API volatility (The Odds API schema changes, Stripe webhook latency). Both are exogenous shocks. The adjudication rule is that the platform's internal invariants must treat them as veto conditions: external volatility never justifies relaxing "no fake data," "no fabricated stats," or server-side paywall enforcement. If the external layer is unavailable, the internal layer shuts down the affected pipeline rather than lowering its evidence standard.
</CROSS_LAYER_VETO_ADJUDICATION>
