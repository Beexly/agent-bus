Environmental/weather layer. Although this is a digital product, viewing context is environmental: bright sunlight, low-light indoor settings, and glare all degrade the physical contrast channel. Weather-adjacent veto condition: if luminance contrast cannot be verified across indoor (\( \sim 300\text{--}500\,\text{lux} \)) and outdoor (\( \sim 10{,}000\,\text{lux} \)) approximations, the release is blocked regardless of desktop performance.

Adjudication hierarchy. Vetoes are not weighted equally. The precedence order is:
1. Legal/compliance veto (guaranteed-win, affiliate, method-leakage, minors-targeting tokens) — non-negotiable, blocks release.
2. Accessibility/biomechanical veto (contrast, tap target, focus, reduced motion) — blocks release because it violates acceptance criteria and legal exposure.
3. Performance veto (LCP, CLS, TBT budget breach) — blocks release because it violates the performance budget [PAGE 1].
4. Conversion/design preference (visual polish, animation density) — advisory only; may not override any veto above.

If any veto in layers 1–3 fires, the feature flag is toggled off or the component is reverted; no production data rollback is needed [PAGE 1]. Conversion upside never outranks a physical or biomechanical veto.

Scenario 1 — Mobile tap-target and focus veto.

Verification: automated mobile screenshot diff plus keyboard navigation script.
Prediction (counterfactual): If deployed despite this condition, mobile bounce rate on /pricing increases by at least 15% relative to baseline, and accessibility complaints or WCAG failure reports emerge within two weeks. The veto prevents deployment, preserving the mobile-layout acceptance criterion [PAGE 1].

Scenario 2 — Copy and compliance veto.
Verifiable condition: Copy scan on /pricing detects any banned token: "guaranteed," "sure win," "lock," "affiliate," source-weight disclosure, private-method reference, or minors-targeting language.
Verification: regex/grep copy scan integrated into CI; manual legal review for nuanced phrasing.
Prediction (counterfactual): If deployed with such copy, the site incurs a legal/compliance breach and user trust erosion; support deflection worsens because users feel misled about cancellation or outcomes. The veto preserves the responsible-gambling and public/private boundaries [PAGE 1].

Scenario 3 — Performance and build veto.
Verifiable condition: typecheck/lint/build fails, or Lighthouse/CI measurement shows \( \Delta\text{LCP} > 0\,\text{s} \), \( \Delta\text{CLS} > 0.1 \), or \( \Delta\text{TBT} > 0\,\text{ms} \) relative to the pre-change clone.
Verification: CI typecheck/lint/build step plus Playwright route probe and Lighthouse audit.
Prediction (counterfactual): If deployed with a performance regression, overall site bounce rate rises and the performance budget is worsened, directly violating acceptance [PAGE 1]. The veto ensures rollback isolation without production-data rollback [PAGE 1].

RLVR reward signal: the verifiable reward is binary—deployment authorized only if all three scenarios return PASS. Any FAIL triggers the feature-flag rollback path [PAGE 1], and the counterfactual prediction is logged for post-deployment comparison against baseline metrics.
