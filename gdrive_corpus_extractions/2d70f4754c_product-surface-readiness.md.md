**1. Route Verification State Function ($\mathcal{S}_{rv}$)**
Let $\mathcal{R}$ be the finite set of all defined application routes (e.g., homepage, board, player pages, GSE Rating page). For each route $r \in \mathcal{R}$, we define a binary state variable $X_r$.
\[
X_r = \begin{cases} 
1 & \text{if route } r \text{ responds successfully to a defined probe (e.g., HTTP 200 OK, expected JSON payload)} \\
0 & \text{otherwise (timeout, 4xx/5xx error, missing)}
\end{cases}
\]
The overall Product Surface Readiness Score, $S_{PSR}$, is defined as the normalized sum of these states:
\[
S_{PSR} = \frac{1}{|\mathcal{R}|} \sum_{r \in \mathcal{R}} X_r
\]
**Units:** Dimensionless ratio, typically expressed as a percentage.
**Assumptions:** All routes in $\mathcal{R}$ are considered equally critical for "readiness." This may be relaxed to a weighted sum $S_{PSR}' = \frac{\sum w_r X_r}{\sum w_r}$ where $w_r$ reflects business-criticality.
**Breakdown Regime:** The definition breaks down if the success criteria for a "response" is ambiguous (e.g., a page loads but displays an empty div due to a frontend JavaScript error). The source text clarifies this by specifying "Missing route proof," implying that mere HTTP response is insufficient; functional proof is required. Therefore, $X_r=1$ should be contingent on passing a suite of behavioral tests defined in the `app-verification-run.md`.

**2. Information Entropy of the Readiness Claim ($H_{claim}$)**
Consider the organization's internal claim about the product's state. Let the true state be $T \in \{ \text{Green}, \text{Red} \}$. Let the reported state be $R$, also in that set. The source text establishes a policy: $R$ can only be "Green" if all BUILD cards are executed (which implies verifying all critical routes). Before execution, there is uncertainty about whether the built routes will *pass* verification.
Define a Bernoulli trial for each critical route $c \in C \subseteq \mathcal{R}$ (where $C$ is the set of currently missing/broken routes) representing the probability $p_c$ that it will pass verification after the build.
The joint probability that all critical routes pass is $P_{all} = \prod_{c \in C} p_c$. If $P_{all}$ is low, declaring "Green" based on incomplete builds has high entropy—it's a guess.
The entropy of the readiness claim before full build execution is:
\[
H_{claim} = - P_{all} \log_2(P_{all}) - (1 - P_{all}) \log_2(1 - P_{all})
\]
**Units:** Bits.
**Assumptions:** Independence of route success (a strong assumption; bugs often cluster). If dependencies exist, $P_{all}$ must be modeled via a Bayesian network.
**Breakdown Regime:** This model breaks if the relationship between "building" and "passing" is not probabilistic but deterministic (either perfect or always failing). In practice, engineering introduces stochastic failure modes. The directive aims to reduce $H_{claim}$ to near zero by forcing empirical verification (setting $p_c \to 1$ or $0$ through testing).

**3. Operational Velocity Under Constraint ($V_{ops}$)**

\[
V_{ops} = \frac{|\mathcal{T}|}{t_{target} - t_{now}}
\]
If $t_{target} - t_{now} < \sum t_i$, then $V_{ops}$ is physically impossible under linear assumptions, indicating a schedule crisis.
**Units:** Tasks per unit time (e.g., cards/day).
**Assumptions:** Task durations are known and fixed. Parallelism is not modeled here.
**Breakdown Regime:** Breaks down if task discovery is dynamic (new bugs found during builds create new tasks). This suggests a need for a buffer or a different metric like cycle time.

*   **The Waterfall Fallacy (1970s):** Early structured programming methodologies often treated detailed design documentation (flowcharts, pseudo-code, interface specs) as synonymous with a completed system. The belief was that if the design was perfect, coding was merely transcription. High-profile project collapses in the 70s and 80s proved this catastrophically wrong. *   **The Agile Manifesto (2001):** A direct reaction to waterfall. One of its four values is "Working software over comprehensive documentation." The GSE directive echoes this but adds a crucial twist: it doesn't dismiss documentation (the evidence files exist and are vital), but it subordinates documentation to working software as the *only* valid indicator of readiness. This is a mature evolution of agile principles.
*   **DevOps & Continuous Integration (2010s):** The rise of automated testing and deployment pipelines created the technical infrastructure to make "working software" continuously verifiable. The concept of a "deployment ready" state became objective (all tests pass, CI pipeline green). The GSE "route verification matrix" (`route-verification-matrix.csv`) is a pure DevOps artifact—it automates the check that a route responds correctly.
